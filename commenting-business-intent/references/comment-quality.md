## 业务理解工作流

在写代码和注释前完成以下步骤：

1. 明确当前需求要求改变或保持什么行为。
2. 定位入口、调用方、数据来源、状态拥有者和最终使用位置。
3. 阅读相关类型、接口契约、测试、已有注释、参考端或历史实现。
4. 写出仅供推理使用的三栏认知：
   - 已证实事实：有需求、契约、测试或代码路径支持。
   - 待验证推断：有线索但缺少闭环证据。
   - 未知：当前材料无法判断。
5. 只把“已证实事实”写成业务注释。对推断继续验证；无法验证时缩小为技术事实，或不写注释。

不要求把三栏认知提交到代码或最终回复，但必须能说明每条业务注释的依据。

## 证据分级

| 证据 | 可支持的结论 | 不可直接支持的结论 |
| --- | --- | --- |
| 用户确认的需求、正式产品/API 契约 | 明确业务规则和对外语义 | 契约未覆盖的例外 |
| 可验证的测试与完整调用链 | 当前系统实际保证的行为和范围 | 产品为何这样设计，除非另有说明 |
| 类型定义、服务端字段说明、参考实现 | 字段/状态含义及跨端约定 | 当前端一定采用相同策略，除非调用链闭环 |
| 相邻代码、命名、单次运行结果 | 调查线索和局部技术行为 | 全局业务含义、长期兼容承诺 |
| 行业惯例、经验、字段名、魔法值 | 仅用于提出问题 | 任何应写入代码的业务事实 |

引用工单号、协议版本或兼容原因仅在其能帮助未来维护且仓库允许时使用。不要在注释中写入账号、Token、真实用户数据或内部敏感信息。

## 何时需要注释

| 语义热点 | 注释应回答 |
| --- | --- |
| 业务门禁、资格、权限、状态迁移 | 为什么在该条件下允许、阻止或转换；影响范围是什么 |
| 边界值、顺序、去重、分页、重试 | 为什么必须保留该边界或顺序；违反后会怎样 |
| 异步、缓存、复用、生命周期 | 哪个迟到结果必须丢弃；谁拥有状态；何时清理 |
| 外部协议、兼容、供应商差异 | 必须遵守哪个约定；为何不能采用更直观写法 |
| 安全、隐私、资金、不可逆操作 | 防范的风险和失败策略是什么 |
| 临时绕行或反直觉实现 | 当前限制、退出条件和可追踪依据是什么 |
| 公共 API | 调用方必须知道的前置条件、结果、副作用和错误语义 |

以下情况通常不写注释：变量赋值、普通 `if`、明显循环、重复方法名、布局数值逐项翻译、只为增加注释数量而写的摘要。

## 注释写作契约

一条有价值的注释按需要包含以下内容，而不是固定套模板：

1. **条件或上下文**：注释在哪种业务状态下成立。
2. **决策或约束**：代码必须保持什么行为。
3. **原因或影响**：为什么这样做，改变后会破坏什么。
4. **作用范围**：结论只属于当前函数、当前端、当前协议还是全局规则。
5. **依据**：仅在未来维护需要时写入稳定的契约、版本或任务标识。

先改善命名、类型和结构，再注释剩余的“为什么”。将注释放在最小且稳定的语义边界旁，避免依赖具体行号或复述实现步骤。

证据不足不自动产生注释。若代码已经清楚表达条件和结果，保持无注释；不得用自然语言重写布尔表达式。只有已验证的局部技术约束非显然、无法通过命名或类型表达且会影响维护决策时，才使用精确的局部表述。

“含义未知、尚未确认、仓库内未找到契约”是调查结论，不是稳定的源码知识。将它们写入交付说明或 review 结论，不要写进源码。只有用户授权且存在任务编号、负责人、兼容风险或明确退出条件时，才提交 TODO 或临时限制说明。

## Swift 示例

假设正式需求和接口契约均确认：首屏服务端排序代表运营优先级，且首屏重复项必须保留；只有后续分页需要避免与已展示 ID 重复。

```swift
func mergeFirstPage(_ incoming: [Room]) {
    // 首屏顺序和重复项均由运营配置决定，投影阶段必须原样保留；
    // 跨页重复只在追加分页时处理，避免改变首屏展示策略。
    rooms = incoming
}
```

这里的注释说明了约束、原因和处理边界。不得只写：

```swift
// 设置首屏房间列表。
rooms = incoming
```

如果只有下面的代码，没有状态码契约：

```swift
return context.accountState != 3
```

不得写“封禁账号不能进入”。字段名和数字不能证明 `3` 的产品含义。先查契约和调用链；仍未知且代码本身已经清楚时，不增加注释。只有在不发明含义的前提下确实改善可读性，才调整命名或提取条件。

## 常见借口

| 借口 | 处理方式 |
| --- | --- |
| “字段名已经很清楚” | 字段名是线索，不是业务契约；继续验证语义和范围。 |
| “负责人让我先按理解写” | 可以按授权实现，但不能把假设伪装成已确认事实；明确假设或只写技术行为。 |
| “时间不够，先补上再说” | 错误注释比缺少注释更危险；无法确认就缩小表述或不写。 |
| “冒烟通过，业务含义就是这样” | 运行结果证明一次行为，不证明原因、状态命名或全局规则。 |
| “reviewer 要一眼看懂效果” | 先让命名和结构表达行为，注释补充有证据的原因与影响。 |
| “多写一点总比没有好” | 噪音会掩盖真正约束；只保留改变维护决策的信息。 |
| “至少可以描述当前代码做了什么” | 代码已能直接表达的行为不需要自然语言副本；改善命名或保持无注释。 |
| “把未知写出来总比不写好” | 将未知放进交付说明；源码注释只保留稳定、可维护的约束。 |
| “这是常见行业规则” | 行业惯例不能替代当前产品契约。 |

## 红旗

出现以下任一情况时，停止写注释并回到证据调查：

- 使用“应该是、通常、看起来、猜测、按字段名理解”后仍把结论写成事实。
- 给数字、布尔字段、字符串码或缩写发明业务名称。
- 把当前函数、当前端或当前页面的行为扩大为全局产品规则。
- 注释只是把代码逐句翻译成自然语言。
- 因为业务证据不足，就在简单表达式旁补一条“当前行为说明”。
- 用“含义未知、未找到文档”满足增加源码注释的要求。
- 注释描述的行为无法由需求、契约、测试或调用路径定位。
- 代码变化后，旧注释仍声称已经不存在的约束。
- 用注释掩盖含糊命名、过长函数或错误抽象。
- 写下没有负责人、任务或退出条件的“临时方案”。

## Review 清单

- [ ] 能指出每条业务结论的证据来源。
- [ ] 已区分事实、推断和未知，没有把推断写成事实。
- [ ] 未知项留在交付说明中，没有变成会过期的源码注释。
- [ ] 注释说明原因、约束、边界或影响，而非逐行翻译。
- [ ] 局部实现没有被表述为全局业务规则。
- [ ] 简单代码通过命名和结构自解释，没有强塞注释。
- [ ] 业务行为变化时，相关注释已同步更新。
- [ ] 文档注释准确描述公共 API 的前置条件、副作用和失败语义。
- [ ] 注释符合仓库语言、格式、lint 和敏感信息约束。
