# UIKit 布局规范

## 核心规则

根据布局关系、更新频率和维护成本选择 SnapKit 或 frame，不强制所有布局使用同一种方式。

1. 需要 Auto Layout 时，优先使用 SnapKit 编写约束。
2. 布局简单、几何关系明确，或属于高频自定义布局时，可以使用 frame 手动计算。
3. 不得让约束和 frame 同时控制同一视图的同一组位置或尺寸属性。
4. 无论使用哪种方式，都必须适配实际容器尺寸、safe area、不同尺寸 iPhone 和 RTL，不得只在单一设计稿尺寸上正确。

除非用户明确要求修改依赖，否则不得添加、移除或替换软件包依赖。受影响 target 未链接 SnapKit 时，不得擅自引入。

## 默认适配范围

- 默认只要求适配 iPhone 竖屏，不把 iPad、横屏或 Dynamic Type 作为完成门槛。
- 用户、设计稿、无障碍目标或适用的仓库规范明确要求时，扩展对应设备、方向或 Dynamic Type 验证；更具体的要求优先。
- 可以使用 `375 × 812` 设计稿校准视觉，但只能把它作为验收基准，不得把设计稿画布尺寸当作运行时屏幕尺寸。
- 即使只支持 iPhone 竖屏，也必须适配不同宽度、高度和 safe area 的 iPhone。

## 修改前检查

1. 阅读仓库指令和相邻 UI 代码，优先保持同一组件内的布局方式一致。
2. 分析父子视图、safe area、layout guide、相邻视图、滚动内容、重叠关系和更新频率。
3. 确认布局是否依赖 intrinsic content size、本地化文本、动态内容或外部视图关系。
4. 明确需要覆盖的最小与最大 iPhone 容器尺寸、safe area、键盘和 RTL 场景；仅在任务范围要求时增加 iPad、横屏或 Dynamic Type。
5. 用户提供运行截图或 View Hierarchy 时，直接对比页面容器、控件本身和内部排列视图的真实 frame，优先修复发生压缩、裁切或留白的那一层。

## 选择 SnapKit

以下情况优先使用 SnapKit：

- 布局依赖父视图、safe area、layout guide 或相邻视图。
- 内容尺寸由文字、图片比例或 intrinsic content size 决定。
- 页面存在本地化长文本、可变内容或复杂的自适应关系。
- 需要更新、重建、设置优先级或执行约束动画。
- 滚动视图的 frame 与 content 尺寸需要通过约束完整推导。

使用规则：

- 使用 `snp.makeConstraints` 创建初始约束。
- 只改变常量时使用 `snp.updateConstraints`。
- 仅在约束关系需要整体替换时使用 `snp.remakeConstraints`。
- 需要频繁修改单个约束时保存对应 `Constraint` 引用。
- 不要在 `layoutSubviews`、`viewDidLayoutSubviews` 或复用回调中重复创建同一组约束。
- 优先使用 `leading` 和 `trailing`，避免使用 `left` 和 `right`。

## 选择 frame

以下情况可以使用 frame：

- 布局是由父容器 `bounds` 可直接推导的简单矩形关系。
- 自定义控件需要在 `layoutSubviews()` 中高频更新子视图位置。
- 自定义绘制、动画、播放器、画布或特殊排版需要精确控制几何结果。
- 使用约束会显著增加复杂度，而手动计算可以保持逻辑清晰、稳定和可测试。

使用规则：

- 在 `layoutSubviews()` 或明确的布局入口中，根据当前 `bounds`、`safeAreaInsets` 和 `directionalLayoutMargins` 重新计算。
- 不得以 `UIScreen.main.bounds` 代替实际父容器尺寸。
- 不得假定固定屏幕宽度、高度、刘海、安全区或导航栏尺寸。
- 将重复的几何计算提取为纯计算方法，输入容器尺寸和布局方向，输出布局结果。
- 内容或容器尺寸变化后必须重新布局，不得缓存只适用于首次尺寸的 frame。
- 避免无界比例缩放；为关键尺寸设置合理的最小值、最大值和内容约束。

## 屏幕与容器适配

- 以当前容器 `bounds` 和 safe area 为事实来源，不以设计稿尺寸作为运行时固定尺寸。
- 默认处理不同尺寸 iPhone、导航栏、Tab Bar、键盘和父容器嵌套造成的可用空间变化；仅在任务范围要求时处理旋转和 iPad 分屏。
- 小屏幕不得出现内容重叠、越界、按钮不可点击或关键内容被裁切。
- 大屏幕不得因无上限拉伸导致布局松散、图片失真或内容远离主要操作区。
- 约束布局避免不必要的固定宽高；frame 布局必须在每次容器尺寸变化后重新计算。
- 对可滚动内容明确可视区域与内容区域，确保最小尺寸下仍可访问全部必要内容。
- 顶部控件优先相对 safe area 或相邻控件布局；底部控件必须避开 Home Indicator。
- 键盘出现时保证当前输入项和必要操作可见；根据页面结构使用 `keyboardLayoutGuide`、约束更新或滚动避让。

## 设计稿尺寸与自适应约束

- 通栏主按钮、输入框、分割线和 Footer 优先约束到实际容器或内容容器的 `leading` 与 `trailing`，不得从设计稿固定宽度直接生成运行时固定宽度。
- 不得把设计基准画布上的行宽写成 `maxWidth`、宽度上限或高优先级宽度约束；只有设计明确要求最大内容宽度时才设置上限，并同时保证超出宽度后居中或按设计对齐。
- 设计表达对称页面边距时必须保持两侧一致，不得因固定宽度与画布宽度的差值产生无业务含义的不对称残差。
- 例如设计基准宽度为 `375pt`、两侧边距均为 `20pt` 时，应写成 `leading = 20`、`trailing = 20`；结果在 `375pt` 容器中为 `335pt` 宽，在 `440pt` 容器中为 `400pt` 宽，不得固定为 `327pt`。
- 对等宽重复元素，先用实际容器宽度减去方向边距和所有固定间距，再按元素数量等分；不得固定整行宽度后只适配窄屏。
- 只有图标、明确的点击区域、控件高度和设计确认具有固有尺寸的局部元素才固定宽高。
- 输入框清除按钮、密码显隐按钮等附件应约束到输入框内部的逻辑尾部，固定的是附件尺寸和点击区域，不是相对整页的绝对坐标。
- 纵向位置优先关联 safe area、相邻组件、内容区域或底部操作区，避免用 `top = 453` 一类整页绝对坐标复刻设计稿。
- 设计确实要求绝对纵向位置时，必须同时验证不同高度 iPhone、safe area、键盘和滚动访问，不得只验证 `375 × 812`。

## RTL 适配

- SnapKit 布局使用 `leading`、`trailing` 和方向性 layout margins。
- frame 布局根据 `effectiveUserInterfaceLayoutDirection` 计算逻辑起始边和结束边，不得把固定 `x` 当作永远从左侧开始。
- 使用 `NSDirectionalEdgeInsets` 表达方向性边距，避免用 left/right 固化语义。
- 文本对齐优先使用 `.natural`；只有设计明确要求时才固定左右对齐。
- 不得仅因 RTL 反转业务数据顺序；只镜像视觉方向和具有方向语义的图标、手势或转场。
- 至少检查一种 LTR 和一种 RTL 语言下的布局、裁切、滚动方向和交互区域。

## 避免布局问题

- 避免歧义、重复、互相冲突和不可满足的约束。
- 尊重 intrinsic content size，仅在默认行为存在歧义时设置 content hugging 和 compression resistance。
- 自定义控件的外部尺寸必须由父布局约束或控件自身 `intrinsicContentSize` 明确给出；不得依赖内部子视图约束“碰巧”反向撑开父控件。
- 不要无理由固定本可由内容决定的宽度或高度。
- 复用视图的布局必须稳定，不得在滚动过程中累积约束或遗留旧 frame。
- 页面离开、状态替换或 Cell 复用后，不得让迟到的异步结果继续修改旧布局。
- 出现 `1pt` 或一个物理像素偏差时，不得为通过截图或测试直接移动控件；先检查 safe area、约束基准、等分计算、屏幕 scale 和像素取整，再修正根因。

## 其他 UI 要求

- 默认不把 Dynamic Type 作为完成门槛；仅在用户、设计稿、无障碍目标或适用的仓库规范明确要求时进行适配与验证。
- 避免无说明的魔法数字；复用现有间距、尺寸、颜色、字体和圆角 token。
- 按照相邻代码约定，清晰分离视图创建、层级设置、样式配置、布局配置和事件绑定。

## 审查与验证

完成前执行以下检查：

1. 确认 SnapKit 与 frame 的选择符合布局复杂度，并且没有共同控制同一几何属性。
2. 确认布局基于实际容器尺寸，不依赖单一设备或设计稿尺寸。
3. 默认检查小屏与大屏 iPhone 竖屏、safe area、键盘和容器尺寸变化时是否存在重叠、裁切、越界或过度拉伸；仅在任务范围要求时检查 iPad、横屏和 Dynamic Type。
4. 检查 LTR 与 RTL 下的边距、对齐、视觉顺序、滚动和点击区域。
5. 检查约束更新、frame 重算、动画、滚动和复用场景是否稳定。
6. 对通栏控件检查两侧约束和设计要求是否一致，确认没有把设计稿宽度误写为固定宽度或产生无意义的不对称边距。
7. 对宽度自适应布局至少验证窄屏、设计基准屏和宽屏三档 iPhone 容器；断言首尾边缘、元素间距和对称性，不得只断言单个元素宽度或只测设计基准屏。
8. 截图、快照或独立单元测试与真机结果不一致时，以实际导航、滚动和 safe area 容器中的 View Hierarchy frame 为证据，不得用基准尺寸测试通过否定运行时问题。
9. 环境允许时，构建受影响 target，并运行与不同尺寸 iPhone、safe area、键盘和 RTL 相关的测试或模拟器验证。
