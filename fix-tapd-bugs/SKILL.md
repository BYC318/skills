# TAPD Bug 修复闭环

按以下顺序执行，始终把 TAPD 的读取、代码修改、人工验收和远端回写分开。除非用户明确确认，不做外部写入、状态流转、上传附件或删除 worktree。

## 1. 建立当前上下文

先在当前对话目录执行只读检查，动态获得仓库根目录、当前分支、当前 worktree、远端基线候选和已有改动；不要假定项目路径、分支、空间、用户或凭据。

```bash
git rev-parse --show-toplevel
git branch --show-current
git rev-parse --git-dir
git rev-parse --git-common-dir
git status --short
git worktree list --porcelain
git remote -v
```

- 当前目录不是 Git 仓库时，说明需要用户指定项目；不要创建 worktree。
- 默认使用当前对话项目和分支；用户可以在任何写操作前明确覆盖它们。用 `git rev-parse --git-dir` 配合 `git worktree list --porcelain` 判断当前目录是否为 linked worktree，不根据目录名猜测。
- 保留已有改动。若它们可能与本批修复重叠，先展示重叠点并等待用户决定，不把无关改动纳入提交。
- 先检查用户调用中是否提供一个可解析的 TAPD Bug 链接，格式通常为 `https://www.tapd.cn/<workspace_id>/bugtrace/bugs/view/<bug_id>`：
  - 提供链接时，从链接解析 `workspace_id` 和 `bug_id`，本次范围固定为该 Bug。直接读取该 Bug，不列出或继续处理其他未完成 Bug；该 Bug 的修复、开发验收及获准的 TAPD 回写闭环完成，或该 Bug 明确拒绝并完成获准回写后，结束本次调用。需要人工决定时只暂停等待，不扩展到其他 Bug。
  - 未提供链接时，执行默认逻辑：使用可用的 TAPD 工具或已配置连接列出当前用户参与的空间；选定空间后分页读取分配给该用户且未完成的 Bug。展示 ID、标题、状态、严重程度、优先级和链接，让用户选择。
  - 链接无法解析、目标不是 Bug 或读取结果与链接不一致时，停止并请用户提供正确链接，不回退到默认批量逻辑。
- 对所选 Bug 重新读取详情：描述、环境、复现步骤、实际结果、预期结果、附件和评论。读取结果是后续判断的唯一 TAPD 依据。

## 2. 审查与分组

结合当前项目的代码、配置、测试、版本信息、相似功能和业务契约审查每个 Bug。先寻找最接近的已有实现和可验证证据，再作结论。

### 风险分级原则

- 描述足以让有经验的工程师合理理解并实施时，确认问题并继续。
- 次要细节优先遵循当前项目惯例、相似功能、平台语义和行业常规；可以采用低风险、可逆且不扩大需求范围的合理假设，并记录关键假设。
- 不主动穷举理论边界，也不因低概率细节阻塞修复。
- 只有不同理解会实质改变功能行为、数据兼容、接口契约、安全风险或修复范围时，才阻塞并提出最少必要澄清。

将每个 Bug 归入下列一种结论，并展示对应证据和下一步：

| 结论 | 行动 |
| --- | --- |
| 已确认真实问题 | 进入分组和修复。 |
| 可按合理惯例实施 | 写明关键假设后进入修复。 |
| 描述不准确或逻辑不严谨 | 给出具体问题和可转发的修订建议。 |
| 存在实质信息缺失或歧义 | 给出最少必要澄清问题。 |
| 与项目实现或契约冲突 | 展示代码、配置或契约证据。 |
| 疑似重复或同根因 | 展示关联关系和建议分组。 |
| 客观不成立或不属于当前项目 | 说明原因与证据，先与用户讨论。 |
| 当前无法确认 | 说明已检查的证据和阻塞原因。 |

需要澄清时，不修改代码或 TAPD。输出可直接转发给测试的提问，等待用户让测试修订。用户通知更新后，必须重新读取 TAPD 最新详情并重新审查，不能只依据聊天转述。

将同一根因、同一预期改动的 Bug 分为一组；不相关 Bug 保持独立。向用户展示分组、假设、影响范围和建议的提交边界，取得修复确认后再处理 worktree。

若已修复的 Bug 被测试重新打开，重新读取最新内容，判断新增信息是原修复遗漏还是新增规则；据此在当前工作区返修或请求拆分范围。

## 3. 准备一个批次的 worktree

只有存在已确认、获准修复的 Bug 分组后才执行此步骤。一批最多一个 worktree。

- 当前已经是 linked worktree 时复用它，不新建、不切换分支。
- 当前不是 linked worktree 且需要隔离时，基于用户确认的动态基线创建一个 worktree；先确认目录和分支名不会与现有工作冲突。
- 调用随 Skill 分发的 `scripts/worktree.sh`。从当前会话的可用 Skill 清单读取本 Skill 的 `SKILL.md` 绝对路径，再定位同目录下的脚本；执行时直接使用解析出的真实绝对路径，不引用外部脚本，也不依赖预设环境变量。
- 向脚本传入 `--repo="$REPO_ROOT" create "$BRANCH" --base="$BASE_BRANCH"`；这三个值都必须来自本次只读检查与用户确认，不能复用旧会话的值。

- 创建前扫描当前仓库的 Podfile；只有发现多个时才要求用户指定相对 `--pod-dir`，并把选择传给脚本。脚本也会执行相同保护检查；worktree 创建后的 Pods、CodeGraph 或 Xcode 初始化失败时，保留 worktree 并报告结果。
- 删除时禁止传递 `--force`，也不执行 `git branch -D`。

## 4. 诊断、修复、验证与提交

在选定 worktree 中逐组工作：

1. 先用系统化调试方法建立失败复现、调用路径和根因证据；不要只按症状修改。
2. 对行为变更先写或更新能失败的测试；若测试不适用，说明原因并采用项目可执行的最小验证。
3. 实施最小修复，避免无关重构或依赖升级。
4. 执行项目规定且与改动匹配的测试、构建和静态检查；读取本次命令退出码和失败数。
5. UI Bug 在能稳定进入目标页面时主动生成修复后截图；不能稳定取得时说明原因，不伪造截图。

为同根因、同改动组创建一个 Conventional Commit；不相关 Bug 各一个提交。提交正文关联该组 TAPD ID 和链接，但不 push。提交前只暂存本次文件，并检查 `git diff --check`。

自动验证完成后，仅报告验证证据和“等待用户逐 Bug 人工验收”。不得因此回写 TAPD，也不得把自动测试等同人工验收。

## 5. 逐单人工验收与返修

维护每个所选 Bug 的人工验收状态：未验收、通过或未通过。

- 只有用户明确说某一 Bug 通过，才可把该 Bug 加入 TAPD 回写候选。
- 用户针对具体 Bug 明确表示“开发验证通过”“已人工验收”时，视为该 Bug 的人工验收通过；Codex 报告的自动测试或构建通过不满足此门槛。
- 未通过的 Bug 保持 TAPD 不变，在同一 worktree 继续诊断和返修。
- 若返修关联本批较早的提交，创建普通的独立修复提交，保留每次修改的审查边界。
- 本技能的闭环不包含 autosquash：不得因验收完成主动建议、询问或执行 autosquash，也不得创建 `fixup!` 提交或改写本批已有提交历史。

## 6. 逐单预览并回写 TAPD

仅对人工验收明确通过的 Bug 创建回写预览。每单分别展示：拟上传截图（若有）、评论是否添加、获准时的评论草稿、目标状态及必要中间状态。目标状态必须符合当前操作者的职责边界；若 TAPD 当前工作流要求先进入“接受/处理”等中间状态，必须在预览中逐步列明。

先确认当前操作者在 TAPD 流程中的职责。默认按开发人员处理：

- 开发验收通过后的目标状态是“已解决”；从“新”开始时按工作流依次流转“接受/处理 → 已解决”，已经处于“接受/处理”时只流转到“已解决”。
- 判断不修复且用户明确批准拒绝时，目标状态是“已拒绝”。
- 不把用户所说的“开发验证通过”“已验收”解释为 TAPD 的“已验证”。“已验证”和“已关闭”属于测试或其他后续角色，开发人员不得代为流转。
- 只有用户明确说明当前由其承担测试角色，并逐单授权目标状态时，才可预览“已验证”；不得从人工验收通过自行推断该权限。

若项目状态名称不同，先读取状态映射和流转细则，映射到同等职责节点并在预览中说明。

评论由用户逐单决定。获准评论只描述实际、用户可感知的修复行为，格式为“已修复：实际行为变化。”；不得写 Commit SHA、固定的人工验收结论、个人归责、调试失败过程、未确认推测或夸张保证。

用户确认单项预览后，按顺序执行：

```text
重新读取该 Bug → 上传获准截图（如有）→ 添加获准评论（如有）→ 流转目标状态 → 重新读取核验
```

- 没有截图时跳过附件；标签永不修改；未通过的 Bug 不改状态。
- 判断不应修复时，先展示原因和证据，由用户与测试沟通。只有用户明确要求拒绝时，才预览拒绝原因、评论和目标状态；再次确认后才写入。
- 回写任一操作部分失败时，立即停止本批所有后续 TAPD 写操作，包括尚未开始的其他 Bug。重新读取失败 Bug 的最新状态，识别已成功和未完成步骤，仅预览该 Bug 的剩余步骤，并等待用户再次确认。不得重复上传、重复评论，也不得因此回到代码修复流程；失败项恢复并核验完成后，其他 Bug 仍保留各自的逐单确认门。

## 7. rebase 合并后的安全清理

仅当全部所选 Bug 均已人工通过、TAPD 回写已处理完毕，并且用户明确告知 rebase 合并完成后，才询问是否清理 worktree。

清理前动态确定本批创建或复用时确认的基线分支，并使用相同的 `origin` 远端更新引用；要求 worktree 完全干净。先运行：

```bash
git -C "$WORKTREE_PATH" fetch --prune origin "$BASE_BRANCH"
git -C "$WORKTREE_PATH" status --porcelain
```

仅在目标 worktree 的 `git status --porcelain` 没有输出时继续。将远端跟踪引用设置为 `BASE_REF="refs/remotes/origin/$BASE_BRANCH"`，确认它存在后，再检查工作已被基线包含：

```bash
git -C "$WORKTREE_PATH" show-ref --verify "$BASE_REF"
git -C "$WORKTREE_PATH" merge-base --is-ancestor "$BRANCH" "$BASE_REF"
git -C "$WORKTREE_PATH" cherry "$BASE_REF" "$BRANCH"
```

祖先检查失败时，只有 `git cherry` 对本批相关提交全部标记为 `-` 且没有 `+`，才能认定 rebase 后的新 Commit 已补丁等价地包含这些修改。存在 `+`、命令失败或范围无法对应本批提交时，都要展示差异并等待用户决定。向用户展示精确 worktree 路径和分支；确认后，使用第 3 节已经解析出的内置脚本真实绝对路径，传入 `--repo="$REPO_ROOT" remove "$BRANCH"`。

不使用强制删除选项。内置脚本从 `git worktree list --porcelain` 按分支解析实际路径，因此也能处理复用的自定义 linked worktree。worktree 删除失败时两者都保留；若 worktree 已删除但安全删除分支失败，脚本返回非零并明确报告“worktree 已删除、本地分支保留”，不得继续强制删除。
