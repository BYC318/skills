# 源码交付与去重集成

## 共享任务交付

共享任务可以在自己的源码分支按需求连续开发，不强制每个组件建立分支。每个原子提交只包含一个完整目的；组件的必要资源、工程引用、检查可以一起提交，不能混入无关需求。跨需求的公共基础独立提交，交付清单列明依赖，禁止循环依赖和无说明的 API 破坏性修改。旧能力可复用时优先复用，不为通信流程新建一套 UI 基础设施。

每份发布清单至少包含：`release_id`、需求 ID/修订、平台、稳定 `repo_id`、实际 Git 对象库/子模块身份、基线 SHA、按依赖排序的 `original_sha` 列表、各提交改动路径/用途/依赖、API 与使用示例、需求或设计依据及资源来源（UI 工作包含设计节点）、实际验证与剩余限制、消费者、清单 SHA256。不同源码仓库分开，不能跨仓库挑选同一个 ID；子模块内提交和宿主 gitlink 更新都明确记录。

主任务在源码中核对完整单个提交差异、父提交和依赖，不只信提交标题。普通交付应为单父提交；merge 提交不作为常规 cherry-pick 输入，需要明确主线与重新整理并验证后的交付。必要基础若没有交付或无法独立挑选，先补齐；不带入无关历史填补依赖。

## 页面任务按需接入

接入前先按 [恢复工具](recovery-tool.md) 扫描未完成请求和历史执行结果，再用 `begin-action` 登记每条源提交在目标 worktree 的执行意图。已有记录或结果未知时不直接重做，先核对真实 Git；实际成功且核验后用 `finish-action` 保存本地 SHA 与依据，再发布 CONSUMED。每条意图与完成回执是本机协作资料，不放进源码提交。

1. 核对角色、源码仓库、分支、工作区和本端提交审查规则。页面独立单元先提交，不把公共同步与页面代码混在一个提交；未完成改动不能擅自 stash/丢弃以便接入。
2. 读取主任务发布的当前 READY、清单哈希和依赖；检查真实 Git 中提交存在、源码身份一致、未处于 cherry-pick/rebase 等未完成操作。先查本地映射，禁止重复执行。
3. 对已批准清单按依赖顺序逐个 `git cherry-pick -x`；不使用提交范围表达式带入未批准历史，不调用 `git merge` 合入整个共享分支，也不直接从其他 worktree 复制活动文件。命令只作用于当前本端 worktree，不含 push。
4. 每个成功动作记录 `(repo_id, original_sha) → applied_sha`、实际文件差异、检查及消息/需求修订。默认 cherry-pick 新建提交，A/B 的公共副本 ID 通常不同；这不是唯一维护者规则被破坏。冲突解决后核对来源标记，`-x` 不能当成自动去重或完整依赖证明。
5. 失败时写 BLOCKED，保留已成功项和当前操作状态，不自动 `--skip`、`--abort` 或用 ours/theirs 覆盖。接收重复通知时核对历史和来源回执，不盲目再次挑选。没有文本冲突也要检查构建、API 和页面行为。
6. 公共实现仍由共享任务维护。页面可配置公开参数和回调，公共缺口重新提需求；发现页面任务私改公共文件或在页面目录复制同类实现，主任务退回处理。工程文件和资源索引也必须事先确定归属，不能只保护组件源码。

命令格式（`真实完整提交ID` 须来自已审查清单）：

```bash
git cherry-pick -x 真实完整提交ID
```

## 页面交付与主任务去重

本节“全部任务完成”指本批已登记参与者完成本批冻结的需求修订，不是全部长期模块未来都没有需求。后续需求复用原任务，批次切换、基线核对与交付撤回按 [长期接续流程](lifecycle.md) 执行；冻结后不覆盖原交付清单。

页面 RESULT 分开提供 `consumed_shared` 和 `page_commits`。前者是原始公共 SHA、本地副本 SHA、需求修订与验证；后者是该页面独有的有序原子提交及实际改动路径/依赖/证据。混合提交不能仅靠标记为“页面”绕过范围检查，应先整理出单一目的交付。

默认集中集成，不边开发边汇总：本次约定范围内所有执行任务完成、共享交付封版、提交清单与所需证据交齐、未完成 Git 操作和依赖阻塞处理完，主任务才冻结集成输入并开始挑选。先完成的任务只交终版资料后等待。原子提交仍在任务内及时完成，不能把“等统一集成”理解为积攒一个大提交。主任务集中挑选每个原子提交，不把它们压成一个提交。

主任务在 `integration.json` 记录参与任务、各终版交付的版本/哈希、是否全部齐备、未解决项和实际集成开始时间。缺一个参与任务的终版交付就保持等待或阻塞；用户明确调整范围时更新原授权范围及排除依据，不擅自划小批次提前集成。后续集成发现问题，定向安排受影响任务修正，按修订清单继续本次集中集成，而不是让所有任务重新互相沟通。

主任务以 [集成记录模板](../assets/集成记录模板.json) 为起点，在明确授权的本地源码集成 worktree 中按以下顺序操作；协作资料仓库的写入及 Git 权限按项目配置和实际用户授权核对，不从源码授权推导：

主任务负责 Git 集成操作及只读核对，不直接修改冲突文件或补写适配代码。发现冲突时保留现场，登记受影响文件及当前 Git 操作，暂停该 worktree 的其他写入，并指定页面或共享代码所属执行者修复；涉及双方契约时先统一契约。主任务核对修复及验证结果后再继续集成，不与修复者并发操作同一 Git 状态。

1. 核对集成基线、干净状态和集成清单；建立“原始来源 → 集成提交”的记录，先记录计划动作，动作后记录实际 SHA。公共项按依赖顺序只接入一次。
2. 分别挑选 A/B 的 `page_commits`，跳过它们的 `consumed_shared` 副本；默认不整分支 merge 页面任务，否则重复公共历史又会被带回。页面提交相互依赖时依赖排序，不靠文件名猜测。
3. 去重主键是稳定源码仓库身份 + 原始完整 SHA。多个原始 SHA 似乎表达同一改动时，辅助检查 `git patch-id --stable`、实际 diff、API 和树状态；patch-id、提交消息中的 `-x` 或内容相似都不能独立证明可安全跳过。有歧义先停下核对，不自动丢弃。
4. 记录每项 `integrated`、`skipped_shared_copy` 或 `blocked`，包含原始 SHA、交付/本地 SHA、规范集成 SHA、理由、实际验证。A/B 的公共副本必须映射到集成中的同一规范公共项。任务超时后先查 Git 与记录补回执，不能重复应用。
5. 不提前将公共原始分支又整体 merge 进来；本批以规范集成结果为后续基线，源分支只是交付来源。未验证前不删除源码分支/worktree，避免丢失未交付工作。不擅自改写用户分支或为清理重复历史做 rebase/squash。
6. 主任务安排执行者对最终集成按项目配置重新构建、测试及复验受影响范围。UI 工作按项目证据矩阵采集运行截图并更新验收册；非 UI 工作提交相应验证产物。源工作区证据保留历史，不能伪称它来自最终集成；沿用项目验收工具，不另建第二套判定。

## 这套选择的代价

它减少交付分支组织要求，但主任务承担按清单选择性集成和去重职责。cherry-pick 不能保证无冲突，目录归属也不能防止公共 API、主题、依赖或工程配置带来的语义问题。已知依赖必须登记；若清单无法准确整理或改动高度耦合，就缩小并发、顺序完成，而不是不断增加消息协议或强行自动合并。

Git 语义依据：[cherry-pick](https://git-scm.com/docs/git-cherry-pick)、[patch-id](https://git-scm.com/docs/git-patch-id)、[worktree](https://git-scm.com/docs/git-worktree)。消息工具不执行这些 Git 动作，实际命令遵守平台规则与批次授权。
