# 长期接续与需求变更

## 长期任务与交付批次

主任务、模块执行任务和共享任务是长期工作单元；批次是其中一轮有边界的交付。需求修订、Git 分支与截图轮次各有自己的标识，不用聊天 ID 代替它们。跨聊天协调主任务维护协调资料并核对交付，不接管已分配给其他任务的源码；模块或共享任务内部主 Agent 可直接实现和验证。页面和公共代码仍由对应任务维护，归属调整先核对在途动作并完成职责交接。

| 资料 | 保存位置 | 内容与维护方 |
| --- | --- | --- |
| 长期任务目录 | 项目配置指定的长期目录 | 主任务维护稳定逻辑 ID、真实聊天/项目/host ID、职责、历史工作区、当前批次、待办及替换关系 |
| 每轮协调资料 | 项目配置指定的独立批次目录 | 每批独立的 `batch.json`、`events/`、`deliveries/` 和 `integration.json`，遵循现有通信协议 |
| 接续说明 | 项目配置指定的接续说明 | 主任务记录当前修订、阻塞、待通知、Git 操作现场、证据与下一步 |
| 验收台账及历史 | 项目配置指定的证据目录与台账 | 主任务核对，执行任务采集；UI 工作接入项目既有截图流程，非 UI 工作接入相应测试及交付证据 |

已有单批 `coordination/` 路径保持原位并登记到目录，不为统一目录形状迁移在途消息。新批次使用隔离子目录，工具的 `--root` 指向该批实际目录。长期任务目录从 [模板](../assets/长期任务目录模板.json) 填入真实信息，模板空值不代表聊天已创建或绑定。仅维护配置时不创建真实聊天或运行批次；实际启动时按当前用户授权登记真实身份及批次，不将配置维护的限制套用到已授权执行。

## 复用原任务

1. 主任务先查长期任务目录，使用实际线程工具核实项目、聊天身份、归档状态与最近交付。追加模块需求继续该模块原任务，公共需求继续原共享任务；不因“上一轮已完成”就新建替代任务。任务标题可变，身份按真实 ID 核对。
2. 只为本轮列入范围的模块安排执行；其他长期任务保留“等待下一轮”，不加入本批等待条件。先完成的任务保存终版清单并结束本轮，不持续空等或逐次催报。
3. 结束一轮后更新目录中的批次、交付与恢复入口，保留聊天，不自动关闭或归档。真实任务不存在、不可用或用户要求拆分时，才考虑经授权替换；先交接、解除原写入归属，记录新旧关系，避免两个任务同时维护同一公共路径。
4. 原聊天可持续复用，源码分支和 worktree 不承诺永久复用。新批次重新核对每端已验收集成基线、未提交改动、已接入公共版本与未完成 Git 操作；需要新源码分支/worktree 时记录前后关系，不重放上一轮已集成提交，也不强制 reset、删除旧工作区或改写历史。

## 追加、调整与取消需求

用户可以在主任务或任一模块任务中提出需求。接收方保存原始用户要求及可核实来源、涉及模块、预期行为和已有差异；UI 工作另附页面/状态及设计节点或快照。向其他任务转述要求不自动扩大授权；接收方须能够核实适用于自己的用户授权，无法核实时保留待核对并继续不依赖它的工作。

主任务统一登记变更并下发修订，不让执行任务各自维护相互矛盾的范围。原授权内正常实现、差异修复、提交与截图按既有流程推进，无需每次重新分派。新的需求决策按下表处理：

| 变更 | 登记与处理 |
| --- | --- |
| 新增独立能力 | 分配新的需求实体 ID，初始修订为 1，记录归属、授权、依赖及验收范围 |
| 调整既有要求 | 保留同一需求 ID，递增修订，记录替代关系、变化原因、受影响源码/消费者/证据及保留行为 |
| 取消要求 | 发布新修订的 `INVALIDATED`，停止旧修订的新动作，核对已实施内容；需要回退时安排所属执行者，不自动丢弃代码或证据 |

模块任务收到追加或调整要求后，使用 `REQUEST` 保存并通知主任务；待主任务明确归属、批次和有效修订后执行变化部分，其他不受影响的原授权工作继续。主任务通过 `ASSIGN` 下发需求，公共交付用 `READY`，撤回旧契约用 `INVALIDATED`，核验并关闭某消费者的依赖用 `RESOLVED`。沿用同一消息协议及 envelope，变更原因、原始授权来源、旧/新修订、影响范围、批次安排放进 `payload`。

调整申请的 `REQUEST.revision` 仍使用本批当前有效修订，建议的新修订放进 `payload`；执行任务不能自行提高 envelope 的修订。由主任务发布新版决策后，执行任务才使用新修订。新批次先由主任务发布有效修订的 `ASSIGN`，再接收执行方事件，避免默认修订 1 与跨批延续的修订冲突。

需求 ID 在长期项目中稳定，修订跨批次继续递增。每个批次配置列出本批参与需求及有效修订，新批首次 `ASSIGN` 使用该有效修订；工具只识别本批事件，主任务还必须核对长期记录及前批最新决策，不声称脚本已经提供跨批事务或全局修订校验。

## 冻结范围与下一轮

- 每轮分派时列出参与者、需求修订、设计依据、必要依赖和验收项，终版交付时冻结清单及哈希。只对这一轮的范围判断“全部完成”，不等待所有长期模块的未来需求。
- 未冻结时，主任务可将用户已授权的新要求登记为本轮修订，更新参与者、影响及交付条件，再通知受影响任务确认。冻结后新增要求默认进入下一批次，并复用原任务；不悄悄塞进已冻结交付。
- 用户明确要求修改当前冻结批次，或本轮验收发现原范围缺陷时，暂停受影响的接入/集成，保留旧快照，撤回受影响交付并登记新修订；收齐更新后的交付及验证再继续。未受影响资料可保留，但必须核对它们的依赖仍有效；不把撤回旧批次当作自动回滚已集成代码。
- 下一批以核实后的集成结果为基线，只登记本轮增量及必要公共依赖。公共改动仍由共享任务原子提交，页面按需接入；本批所有参与任务交付完再集中集成。Git 集成方式继续遵循 [源码交付规则](code-delivery.md)，长期接续不授权改变集成策略或改写用户分支。

## 证据与恢复

需求或公共实现变化时，主任务列出直接和间接受影响的验收范围，使相应旧证据失效，并运行项目配置指定的检查及报告工具。保留旧证据及真实构建元数据，复验产生新轮次。UI 工作按该项目要求的页面、状态、平台和显示组合重新取证并更新验收册；非 UI 工作重新验证对应契约、测试与产物。未完成复验不能沿用上一轮“通过”，没有受影响的证据也须核对适用条件。

中断前，各执行任务在自己的交付/事件中保存当前需求及修订、实际提交、未提交文件、Git 操作现场、公共版本、截图轮次、阻塞和下一步；主任务将索引写入接续说明和长期目录。恢复时按“任务目录及真实聊天 → 当前批次和有效修订 → 持久事件及待确认通知 → 实际源码/Git → 证据文件 → 下一动作”核对，不只读聊天总结或旧的完成标记。

主任务暂未运行时，模块可保存请求并继续不受影响的工作；跨模块变更等待协调，不能声称有后台自动调度。任务目录与变更记录由 Agent 按流程维护，现有信箱脚本校验消息并汇总已落盘恢复事实；本流程不提供自动任务发现、跨批调度、应用截图或文件权限隔离。

独立聊天内部曾派生子 Agent 时，所属主 Agent 还须核对其当前状态、源码改动和在途写入；聊天中断或缺少最新汇报不代表原子任务已停止。重新派生不是默认恢复动作：先确认是否仍需原执行者继续，状态不明则保留待核对，不重复分配同一写入范围；确需替换时先停止或交接旧职责，记录新旧执行者与实际进度。长期聊天身份、内部子 Agent 标识和交付批次继续分别记录。

## 中断与反复纠正后的恢复对账

暂停任务、聊天继续讨论和需求撤回是不同事实。暂停某执行任务不会自动取消它此前提出的依赖请求，也不证明主任务或共享任务已经停止。后续要求未明确提到旧依赖时，旧依赖仍保留为未关闭项，核对新要求的影响后才能继续消费；不能默认为已取消或仍完全兼容。

### 未关闭请求必须有去向

执行任务在自己的事件和接续记录中保留对外请求；主任务在长期任务目录的 `open_dependencies` 中维护索引，关联需求 ID/修订、请求消息、提出方、实际使用方、负责方、当前状态、交付/接入回执及下一动作。不同消费者分别记录，A 取消使用不等于 B 也不需要。表格或 JSON 均可记录事实，不要求每次普通提交新增通信。

每次通信先保存事件再通知；请求状态须区分已落盘待通知、已通知待确认、已确认待交付、已交付待接入、已接入待验证与已完成。只存在 ACK 不能关闭依赖；共享任务做完也不能证明页面任务已接入。只有核实消费与验证结果，或根据用户要求明确取消、替代或移出本批并保留后续去向时，才能关闭本批待办；完成判定须核对未关闭项，不依赖摘要中是否提到它。

### 突然中断也能查证的范围

不能依赖 Agent 在用户点击停止前一定有机会写收尾记录。准备分派、发送通知、接入提交等动作时，先保存意图和关联实体，动作后补实际回执；中断发生在两者之间时状态为待核对，恢复先查真实结果，不盲目重做或认定失败。现有消息已经落盘而通知未发送时，重扫信箱仍能找到；尚未落盘的用户纠正则须从原聊天实际内容补录，不能声称仅靠文件就能找回。

### 每次恢复的必做步骤

1. **核对身份与最近纠正。** 找到原任务、当前批次和最后可信检查点；读取检查点之后的实际用户要求及执行输出，必要时翻查更早消息，避免只读长聊的最后一句。将未登记的纠正连同来源补入变更记录；消息缺失或被截断不能作为“没有变更”的证明。
2. **核对当前契约。** 对照长期需求修订、批次决策与最新用户要求。纠正是否只影响本任务，是否改变公共 API、页面状态、资源或消费者，必须明确。尚未完成协调的变化部分等待主任务处理，独立的原授权工作可继续。
3. **逐项检查未关闭请求。** 合并接续记录、持久事件及长期目录，不只看当前收件箱。检查自己发出的请求，也检查主任务/共享任务后来回复的交付、撤回及待确认消息；为每项旧请求标注保留、修订、取消或待核对，并登记负责方及下一步。目录与事件不一致时用实际消息和执行结果查证，不静默删项。
4. **核对已发生动作。** 请求被调整时，确认共享任务是否已开发/提交/发布，消费者是否已接入及截图是否仍有效。新修订不会自动撤销旧代码；需要通知的受影响者分别登记，尚未确认时不声称已经停工或切换。旧通知不得重新触发已完成动作，已发生但未记录的 Git 结果先补回执。
5. **保存恢复结论再继续。** 对外给出简短摘要：当前有效要求、已完成事实、未完成依赖及等待对象、已变更/撤回内容、下一动作。记录核对过的消息范围及未解决缺口。无歧义时自主继续，不为摘要逐次索要用户批准；关键事实仍缺失时只暂停依赖它的动作并针对性澄清，不凭空补齐。

主任务恢复时对本批所有参与者和未关闭依赖对账；模块任务恢复时先核对自己的职责、对外请求与收到的回复；共享任务恢复时核对每个需求的有效修订及消费者。先运行 [恢复工具](recovery-tool.md) 自动汇总已落盘请求、分派、消息、执行意图和明确的关闭结论，有长期目录时扫描全部登记批次；再补录未落盘的实际聊天纠正并核实真实 Git 与证据。脚本不自动理解聊天或验证业务真伪，不能宣称已经实现完全自动、永不遗漏的调度系统。
