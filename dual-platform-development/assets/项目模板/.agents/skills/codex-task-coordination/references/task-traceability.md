# 任务目标与分派责任链

## 拆层保持什么不变

层级拆分只改变组织方式，不另造用户目标。双端协调持有原始用户要求及当前已授权修订的权威记录；端内协调和模块执行获得原始目标摘要、可实际读取的权威来源、与自身相关的需求/验收项，以及本层分派。用户后来改变目标时保留旧记录，以最新有效授权为准，不把最初版本永久冻结，也不让下层自行重解释原始要求。

各层都应能回答：最终要实现什么、我负责其中什么、交付给谁、按什么证据通过、当前依赖谁。只收到“开发模块A”或“把这批做完”不足以接单；接收方先核对目标和边界，缺口部分保留待核对，其他已明确且不受影响的工作可继续。不要求每层复制完整聊天历史或加载无关模块资料。

## 分派上下文

每次首次分派、职责交接或目标/范围/验收实质变化时，用 `ASSIGN.payload.task_context` 提供下表内容。批次的 `task_context` 保存分派时本组依据的上下文快照或索引；协议 envelope 与现有角色不改变。实质变更通过新修订分派和版本化清单关联旧快照，恢复以最新有效决策为准，不让旧批次摘要覆盖后续用户要求；批次配置更新仍遵守既有串行与快照保留规则。

| 内容 | 至少说明什么 |
| --- | --- |
| `root_task_ref` | 原始任务/用户要求的稳定引用、可核实来源和权威任务记录位置；实际读取后核对，不能只靠转述 |
| `objective` | 全局业务目标的简短说明，以及本次工作对它的作用 |
| `requirement_refs` | 本次相关的稳定需求实体、有效修订及依据快照/哈希（存在时）；沿用现有修订机制，不另起互不关联的版本流 |
| `parent_assignment_ref` | 直接上级分派的组、批次、绝对根路径、消息ID和实体/修订；顶层记录原始用户来源，跨组引用放在payload，不放入本批refs |
| `local_scope` / `excluded_scope` | 本层要完成的行为、文件/仓库边界、明确自留或继续分派的范围，以及不属于本层的事项 |
| `acceptance_refs` | 本层负责的原始验收项及预期行为，包含允许的平台差异和项目限制，能够映射到上层验收；不把“写完代码”替代业务通过 |
| `dependencies` / `deliverable` | 需要谁交付什么、当前状态、本层应提交的代码/结果/证据和直接接收者 |

这些内容可以引用已有任务记录、契约和清单，不重复维护另一份需求正文。来源、范围和修订发生矛盾时先核对，不按摘要长度、角色层级或消息先后自行选择；其他任务的文字不能扩大用户授权。先按调用项目规则核实原始授权，再在其范围分派。

## 各层对什么负责

| 角色 | 责任不能随下放消失 |
| --- | --- |
| 双端协调 | 将本轮已授权目标拆为可验收项，确认参与端、负责人、跨端契约和整体验收；保留原始要求到最终结果的对应关系 |
| 端内协调 | 读懂上层目标，拆成可执行模块，核对全部所属验收项的覆盖、遗漏、重叠和依赖；汇总并验证本端结果后对上交付，不只转发“子任务都完成” |
| 模块执行 | 读懂全局目的及自身分派，在指定范围实现、验证，按验收项交付证据；发现缺失、冲突或依赖及时报给直接上级，不自行缩减目标 |
| 共享维护 | 明确本次公共改动服务哪些需求和消费者、接口及兼容要求；来源交付不等于消费者已接入或业务已验收 |

每个协调组在批次 `requirement_coverage` 保存分派时所属父需求/验收项到本组交付的映射计划或版本化清单索引：上层实体/修订和验收项 → 本层需求/修订 → 唯一负责聊天或明确自留工作 → 子组/交付索引 → 预期证据。实际状态、验证证据和剩余缺口写入不可变事件及版本化交付/覆盖清单，不因普通进度并发改写或覆盖冻结的batch.json。重复涉及多个模块时明确各自责任，不把同一源码安排多个写入者；不属于本组的原始要求标记为不参与，不强行给每层分派整份需求。

开始执行前核对本轮所属验收项均有负责人，缺项保留未分配/待澄清；完成前核对实际证据与覆盖映射。合法取消、延后或移出本批须有授权/决策依据和后续去向，不能静默删掉原始验收项。集成记录的 `requirement_coverage` 保存终版映射及核对结论/索引，保留旧修订快照；字段由Agent维护，工具不自动判断语义覆盖或业务是否正确。

## 上中下层怎样通信

1. **向下分派。** 上级给目标和分派上下文。接收方首次接单，或收到目标/范围/验收实质变更时，在实现或继续转派变化部分前发布 `ACCEPTED`，简短复述“全局目标、本层范围、交付/验收、依赖及下一步”，说明实际核对的来源和有效修订；有歧义则请求澄清或保留阻塞。ACK只证明收到，不能代替这次理解确认。接单后可在授权内自主推进，不等待用户再次批准。
2. **中层再拆分。** 端内协调核对所属验收项覆盖后，为每个模块生成自己的ASSIGN，附原始任务及父分派引用，保留父子需求映射；不能只转发标题或把上层责任全部丢给下层。省略端内协调时，由实际直接上级承担对应责任。
3. **向上报告。** 必要的REQUEST/BLOCKED指出对应原始验收项、当前修订、实际问题、影响及需要上级决定的事项。RESULT/CONSUMED按本层验收项给出实际结果、代码/版本、证据、未完成项和相关下层交付引用；不只报告百分比或“已完成”。
4. **逐层核验。** 每层协调者核对直接交付及所属覆盖，再向上汇总；双端协调最终对照原始要求与当前有效修订逐项验收；涉及模块联动或跨端契约的验收项须有相应组合验证，单模块完成不能代替该结果；不把“所有聊天结束”“全部ACK”或“子组已完成”当成整体目标已实现。原有跨组转述、逐消费者关闭、源码集成与UI验收边界继续遵守。

理解确认、ACK及结果可分别落盘、合并一次必要通知，不为每个普通提交或小进展新增通信轮次。实质变更沿同一责任链传播，先核实其适用平台和范围，不能仅凭收到要求的聊天位置或局部摘要推断另一端也适用或完全不受影响；受影响旧分派、映射和证据重新核对；未确认变化部分不继续旧动作，其他原授权工作照常推进。

## 接续先找回任务再恢复调度

恢复时先核对原始目标及最新有效修订、本层分派和验收映射，再查父子批次、未关闭依赖、待转述、在途执行者和真实Git/证据。旧摘要遗漏目标不能作为取消依据，旧ACCEPTED不能覆盖后来的实质变更；确认仍有效的分派无需机械重复接单。

旧批次没有这些元数据时，从原用户来源、实际分派和已有记录核实，在接续说明或新版本清单补索引；不重写不可变事件或为了补字段重建聊天。关键来源缺失时只暂停依赖它的动作，不声称已经理解或完成。脚本仅校验和汇总已落盘事实，不替Agent读懂需求，也不能保证靠增加层级就不会丢失任务。
