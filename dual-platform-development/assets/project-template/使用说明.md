# 双端开发使用说明

本目录负责协调已有 iOS、Android 工程；各端仓库继续支持同事独立开发。尚未绑定时只作为模板，不代表已经接入或验证 App。

## 入口、流程与独立技能的职责

| 入口或能力 | 负责什么 | 何时使用 |
| --- | --- | --- |
| `dual-platform-development` | 初始化或更新双端协作入口、项目说明、技能与模板；只维护配置，不开发或构建 App | 用户主动要求初始化、更新或维护协作配置时使用，配置完成后停止 |
| [双端开发流程](resources/references/dual-platform/工作流程.md) | 日常双端开发、跨端参考、共同契约、任务内 Agent 分工、UI 截图证据、验收册与接续 | 从双端入口开展相关任务时按需使用，无需每次点名 |
| [codex-task-coordination](.agents/skills/codex-task-coordination/SKILL.md) | 较大需求的多级独立聊天、模块归属、需求修订、批次、持久通信、交付、分层集成与恢复 | 用户主动点名、明确要求使用，或明确继续此前已启用的协作任务；正常接续无需重复点名 |

初始化技能部署或更新项目本地能力，日常开发由 `AGENTS.md` 引导读取本地双端开发流程。启用 `codex-task-coordination` 后，它负责跨聊天推进，本地双端开发流程继续指导每个聊天内部的执行，两者可以同时使用。普通开发、UI 对齐、已有任务目录或技能安装不会自动启用独立任务协作；仅讨论或维护技能不启动真实任务，实际创建、通信与集成遵守用户授权。

## 初始化与更新

用户主动调用：

> 使用 $dual-platform-development 初始化这个 App 的双端协作配置。

或：

> 使用 $dual-platform-development 更新协作配置，保留已有项目规则与各端技能。

配置维护按语义合并，不覆盖定制或清理个人补充技能；再次更新不追加重复规则或技能副本。仅缺失且阻塞当前配置的信息需要补问。工程未指定时保持未绑定，不猜用历史 App。

## 三个入口与技能维护位置

| 使用者 | 工作入口 | 平台能力来源 |
| --- | --- | --- |
| 双端开发者 | 双端协作目录 | 结合根补充技能，按实际路径读取两端既有规则和技能 |
| iOS 开发者 | iOS 源码仓库 | 本仓库规则及 `.agents/skills/` |
| Android 开发者 | Android 源码仓库 | 本仓库规则及 `.agents/skills/` |

根 `.agents/skills/` 可以保存双端协调能力和你为本协作入口维护的补充技能，包括 iOS、Android 专项能力。源码仓库既有平台技能保持原位，按路径复用，不复制、镜像或建立软链接。单端仓库无需依赖双端目录。各端仓库可位于外部位置，不要求搬到固定目录或改名为 `iOS`、`Android`。

已被当前会话发现的根补充技能，按名称、描述与任务选择，不必在 `iOS/AGENTS.md` 或 `Android/AGENTS.md` 逐项登记；仅在需要固定使用、消除歧义或补足发现范围时写读取指引。根入口保留启用条件和项目要求，详细方法与配套资料放在下列目录；独立技能继续保留完整技能包。

### 双端任务如何读取各端配置

各端配置仍由源码仓库维护，双端任务按实际涉及的平台读取并纳入上下文；单端独立开发由本端 Agent 配置决定。

1. 从 [双端项目说明.md](双端项目说明.md) 确认实际工程、源码仓库、Git 根目录及本次各端角色，未绑定或不存在的路径不作为执行目标。
2. 从源码 Git 根目录到目标目录逐级读取适用规则，每级优先 `AGENTS.override.md`，否则读取 `AGENTS.md`；非 Git 工程从约定工程根目录开始，范围变化时补读。
3. 读取本协作目录对应的 [iOS 补充](iOS/AGENTS.md) 或 [Android 补充](Android/AGENTS.md)，与源码适用规则一起作为本次协作依据。
4. 按任务选择源码端技能、根补充技能或其他可用能力，实际读取选中技能的 `SKILL.md` 和必要资源，纳入上下文并按适用范围执行。已有技能索引可利用，没有时检查名称与描述，不要求给源码端新增索引。

发现或匹配到技能元数据不等于正文已经加载；按路径读取也不等于自动注册，不能假设 shell `cd` 会重载规则。用户级或插件能力按实际来源和可用性引用，本机安装不代表同事已安装；缺失或不可读时明确标记，不声称已加载，不默认批量安装。

```text

├── resources/

│   ├── references/
│   │   ├── dual-platform/工作流程.md
│   │   └── ui-alignment/ui-evidence.md
│   └── scripts/
│       └── ui-alignment/
│           ├── ui_evidence.py
│           └── test_ui_evidence.py

```

`AGENTS.md` 是双端总入口，按本次平台读取 `iOS/AGENTS.md` 或 `Android/AGENTS.md`，再按真实源码路径读取源码规则和匹配技能。根 `resources/` 维护公共流程、模板和工具；各端专用资料放在对应平台的 `resources/`，有实际资料时才创建，公共资料按路径共用。UI 资料在公共资源中使用 `ui-alignment/`，不再注册为 `dual-platform-workflow` 技能。独立技能仍保留完整包并位于 `.agents/skills/`。本次配置和模板目录使用英文名，文档内容与文件名保持原语言。

本次结构调整不保留旧命令、旧路径或兼容入口。已有旧配置须按新版重新安装，先把项目定制合并到 `resources/`，再移除旧普通资料目录和旧 `dual-platform-workflow` 包；不迁移旧任务，安装后新开任务。重新安装配置本身不创建任务、不构建 App，也不触发独立聊天协作。

## 日常开发与接续

直接描述目标，例如“参考 iOS 给 Android 补齐收藏”“开发两端收藏列表”“核对两端差异”或“继续上次任务”。不再调用初始化技能；Codex 按本项目入口和本地能力开展工作，只询问当前缺失的必要信息。

未采用独立聊天协作时，两端工作独立且较大、契约和文件边界明确，可按项目规则派生 iOS、Android 工程师 Agent，由当前聊天主 Agent 协调并验收；采用独立聊天协作时不再重复安排同职责执行者。

当前聊天根据已分配工作的规模与依赖选择直接执行或派生子 Agent；启用独立任务协作后，每个模块或共享聊天仍可采用这两种方式。

- 单 Agent、模块或共享任务内部主 Agent 可在自身授权和源码范围内直接实现、修复、构建和验证，也可委派子 Agent；工具不可用时可继续自身尚未委派的工作。
- 派生时提供目标、实际工程与 Git 根目录、适用规则及技能路径、共同契约、允许修改范围、验收项、验证入口和产物约束，不假设自动继承上下文。子 Agent 返回改动、验证证据及阻塞，由所属聊天核对、汇总并对外交付。
- 多 Agent／多独立任务中的协调者负责调度、审查、证据核对、协作资料及已授权集成，不接管已分配给其他执行者的源码，明确留给自己的独立工作仍可执行。调整分工前核对在途动作和工作区，确认原执行者停止相关写入并记录交接；执行者不可用不自动转移归属，已有公共路径继续保持指定的唯一维护归属。

保留现有项目架构与风格，按复用、改造和新写的整体成本选择，兼顾迭代、冗余、耦合、性能及验收成本。官方契约遵守，推荐实践结合项目采用；实质取舍才记录简短依据，不为小任务增加报告。

平台实现、构建和设备验证由各端规则及技能指导，遵守当前环境的产物路径和工程限制。只读参考不产生该端构建义务；技能可用、工具可调用、编译、模拟器、真机和业务验收分别记录。范围外平台不列为未完成开发。

持续任务使用本地模板记录进度与证据。恢复时核对当前工程、Git、证据、旧子 Agent 状态及在途写入；聊天中断不证明原执行者已停止，状态不明时不重复分配同一写入范围，确需替换时先停止或交接旧职责并记录替换关系。启用独立任务协作时，先按 [独立任务接续协议](.agents/skills/codex-task-coordination/references/lifecycle.md) 核对长期聊天、批次和未关闭依赖。提交、推送、PR、发布及外部回写遵守用户当前授权。

## UI 对齐、截图与交付

直接提供本次目标和 Figma 链接，例如“对齐两端登录页，并按项目流程保留截图和验收册”。Agent 会读取 [逐页证据流程](resources/references/ui-alignment/ui-evidence.md)，登记页面及设计状态，调用已有平台工具实现和截图，再用随附脚本检查并生成验收册。

每个设计状态必须保留浅色／深色 × LTR／RTL 四种组合；LTR 使用英语、RTL 使用阿拉伯语，双端共 8 张运行原图。缺少设计依据、截图或实际审查时，记录待办，不宣布完成。已有项目另有明确语言定制时，配置更新保留并列出差异，不自行放宽矩阵。原图和报告放在项目约定的外部目录，台账与接续记录放在 `任务记录/`；未绑定工程时只部署能力，不生成 App 证据。

按批更新台账；准备宣布本任务 UI 全量完成时运行 `deliver`，得到本轮交付回执和归档验收册；验收或接续时用 `verify-delivery` 核对文件和记录是否仍有效。中途汇报不要求每轮生成回执。脚本不自动操作 App，不判断审查文字是否真实，也不安装对话结束后的自动检查；视觉和点击结果仍须实际检查。当前截图交付工具要求参与端有真实 Git 提交 ID，非 Git 工程的构建身份暂不支持。

通用脚本、验收册模板和流程维护在 `dual-platform-development/assets/project-template/`，项目日常运行使用本地副本。后续先改通用原稿，再由用户主动更新项目配置；逐项保留清理方式、授权、路径、额外验收和历史台账，冲突明确列出。更新配置不会自动开始 UI 开发、截图、提交或推送。

## 主动使用独立任务协作

仅在用户主动调用 `codex-task-coordination` 或明确接续已启用协作时使用。先做 [启用价值评估](.agents/skills/codex-task-coordination/SKILL.md#启用价值评估)，再决定是否创建或复用独立聊天；以下是组织方式的说明，不是固定建群清单，也不构成执行授权。

### 角色与数量如何理解

| 角色 | 负责什么 |
| --- | --- |
| 双端协调 | 共同需求、跨端契约与依赖、最终联合验收；通常由当前聊天承担 |
| 端内协调 | 按需协调本端多个模块、端内依赖及所属仓库集成，不是每端必设 |
| 模块执行 | 在分配范围内实现、验证及交付模块；各模块可分别追加需求与长期接续 |
| 仓库内共享 | 按需唯一维护同仓库多个执行任务共同需要修改的公共代码 |
| 跨仓库公共依赖 | 按需维护多个仓库共同消费且本轮需要修改的真实公共来源 |

“主任务”或 `main` 在协议中指当前协调组的协调角色，角色身份以实际目录与批次为准。每个独立聊天内部都可按工作量直接执行或派生子 Agent；子 Agent 是聊天内执行者，不是下图的独立聊天节点。

各层都保留原始目标及有效验收的引用，并明确本层范围和交付对象；首次接单或实质变更先确认理解，中层核对模块覆盖后汇总，最终仍对照原始要求验收，详见 [任务目标与分派责任链](.agents/skills/codex-task-coordination/references/task-traceability.md)。

任务数量先按独立交付单元确定，再核对文件重叠、契约成熟度、公共依赖和资源容量。合并过小或强耦合的单元，协调与共享角色分别计数；长期模块总数、本轮参与数及并发上限也分别记录。创建前简要说明各端数量与拆分收益，不按页面数或平台名称凑任务。

### 窗口名称如何识别职责

独立聊天统一用 `需求简称｜平台 任务角色｜具体模块`，例如 `应用改版｜双端总协调`、`应用改版｜iOS 总协调`、`应用改版｜iOS 子模块任务｜登录`、`应用改版｜iOS 共享任务`；Android 同理。当前协调窗口也按实际覆盖范围命名，模块执行写具体负责模块。创建、复用和接续的命名及身份登记统一遵循[窗口命名规则](.agents/skills/codex-task-coordination/references/hierarchical-coordination.md#独立聊天窗口命名)，下文图示中的角色名仅说明结构。

### 先判断是否值得拆成独立聊天

| 场景 | 默认选择 |
| --- | --- |
| 小改动、一个集中任务，或必须紧密顺序推进 | 当前聊天直接完成 |
| 一次性、有边界的内部并行工作 | 按需派生子 Agent，无需长期独立聊天 |
| 多个较大模块，能独立实现/验收或需要分别长期接续 | 评估使用独立聊天协作 |
| 模块很多但频繁改同一文件、依赖未明确 | 合并任务、减少并行，必要时顺序完成 |
| 全局只有一个执行单元，但用户明确需要独立窗口 | 可以轻量保留，不增设空协调层或共享任务 |
| 已有长期协作，本轮只需一个模块 | 先恢复并复用原聊天，不直接撤销分工或归档 |

一个子聊天不必然只有一个执行单元：当前聊天若明确保留一部分开发，另一个聊天负责另一部分，两者仍是不同执行单元；协调者不能接管已分配源码。调用技能不强制建批次，不采用独立协作时在当前聊天说明选择即可。

### 两端执行数量的基本组合

下表用 0、1、多个覆盖本轮参与情况，数量仅指模块执行单元，不含协调与共享角色。0 表示本轮不参与；以下默认两端源码仓库独立，仓库结构不同的情况见后文。

| iOS | Android | 组织方式 | 端内共享选择 |
| --- | --- | --- | --- |
| 0 | 0 | 仅讨论、核对或规划，不创建开发聊天 | 不启动 |
| 1 | 0 | 本端独立开发由 iOS 自身配置决定；既有双端任务的局部批次复用原分工 | 不因数量单独新增 |
| 0 | 1 | 本端独立开发由 Android 自身配置决定；既有双端任务的局部批次复用原分工 | 不因数量单独新增 |
| 多个 | 0 | 本端独立开发由本端配置决定；既有双端协作按本轮实际范围参与 | 仅真实共同改动时考虑 |
| 0 | 多个 | 同上，不在双端说明中另定本端独立开发规则 | 同上 |
| 1 | 1 | 值得启用协作时，由双端协调直接对接两个模块执行聊天，省略端内协调 | 两端都不启动，本端公共代码调整由对应模块执行承担 |
| 多个 | 1 | iOS 按协调负担选择是否设置端内协调；Android 模块执行直接对接双端协调 | 仅 iOS 可能需要 |
| 1 | 多个 | Android 按协调负担选择是否设置端内协调；iOS 模块执行直接对接双端协调 | 仅 Android 可能需要 |
| 多个 | 多个 | 两端分别评估，可都有端内协调、仅一端有或都没有 | 两端分别按实际依赖判断 |

多个模块不自动要求增加端内协调；双端协调能够清楚管理时，可以直接对接各模块执行聊天。新分工中的公共代码按表安排，既有共享维护归属先恢复，调整时完成交接，不直接转移源码。

### 共享依赖与仓库结构

共享选择叠加在上表上，完整职责以 [两类共享任务条件](.agents/skills/codex-task-coordination/SKILL.md#共享任务的职责与触发条件) 为准。

| 实际情况 | 处理方式 |
| --- | --- |
| 没有公共改动，或本轮只是调用已有公共组件 | 不启动共享开发聊天 |
| 一端只有一个模块执行，需要修改本端公共组件 | 该模块执行完成，不另开端内共享聊天 |
| 一端多个模块共同需要修改同一公共实现 | 评估设一个仓库内共享聊天，统一开发、按清单消费 |
| 两端分别存在上述公共改动 | 各仓库分别确定维护者，不把两套原生实现混成一份共享代码 |
| 两端功能、组件名称或行为相同，但实现各自独立 | 模块执行分别实现，双端协调对齐契约 |
| 仅需要约定接口字段、状态或交互规则 | 由双端协调处理，不额外建立共享代码聊天 |
| 多仓库消费真实公共协议、SDK或共享源码，本轮需要修改来源 | 按需设置跨仓库公共依赖聊天，各模块执行负责本仓库接入/适配 |
| 公共来源存在，但本轮不修改 | 核对版本与兼容性，不启动该来源的开发任务 |

两类共享可以同时存在，也可以都没有；按真实来源和维护边界安排，不为每个组件固定建聊天。

| 仓库结构 | 共享与隔离判断 |
| --- | --- |
| 两端独立 Git 仓库 | 端内公共代码分别维护；跨仓库共享须有真实公共来源 |
| 两端在同一 Git 仓库，代码互不依赖 | 按模块分工，不因同仓库就增加共享任务 |
| 两端在同一 Git 仓库，共同修改同一份公共代码 | 可设一个覆盖双方的仓库内共享聊天，由共同上级协调；即使每端各一个模块，也不应各自重复实现 |
| 嵌套仓库或 submodule | 按真实 Git 根确定归属与独立 worktree；公共源码维护和消费者依赖更新分别记录 |

“两端各一个模块不设端内共享”指每端内部没有多个消费者，不排除两端确实共用同仓库代码或跨仓库公共来源；判断依据始终是真实代码来源。

### 独立聊天图示

每个节点代表一个独立聊天；模块 A、模块 B 必须分别占一个节点。以下是示例结构，标有“按需”的节点仅在触发时设置，省略节点后由直接上级承担相应协调；不把示例当成已经创建的任务。

两端各一个模块，双端协调直接对接，不设端内协调或端内共享：

```text
双端协调聊天
├─ iOS 模块执行聊天
└─ Android 模块执行聊天
```

iOS 多模块、Android 一个模块；Android 多模块时可对称采用：

```text
双端协调聊天
├─ iOS 端内协调聊天（按协调收益选用）
│  ├─ iOS 模块执行 A 聊天
│  ├─ iOS 模块执行 B 聊天
│  └─ iOS 仓库内共享聊天（有共同改动时）
└─ Android 模块执行聊天
```

两端多个模块、均选用端内协调；两端共享分别按需设置：

```text
双端协调聊天
├─ iOS 端内协调聊天
│  ├─ iOS 模块执行 A 聊天
│  ├─ iOS 模块执行 B 聊天
│  └─ iOS 仓库内共享聊天（按需）
└─ Android 端内协调聊天
   ├─ Android 模块执行 A 聊天
   ├─ Android 模块执行 B 聊天
   └─ Android 仓库内共享聊天（按需）
```

两端各一个模块，但本轮确需修改两端共同消费的公共 SDK：

```text
双端协调聊天
├─ iOS 模块执行聊天
├─ Android 模块执行聊天
└─ 公共 SDK 跨仓库依赖聊天
```

最后一种仍不设置端内共享聊天。更复杂的结构按上述模块数量和真实依赖组合，不为展示完整层级额外建聊天。

### 目录、聊天与分支如何对应

新任务的 `worktree/` 与原源码仓库并列，按真实源码所在父目录组织，例如 `<源码仓库父目录>/worktree/应用改版/iOS/iOS子模块任务_登录/`；两端源码父目录相同时可共用，不同时分别登记。只有源码本来位于 `test/` 下才是 `test/worktree/`，不固定跟随协作配置目录。真正需要跨端公共来源维护时，才增加同需求下的“双端共享任务”。共享目录和聊天均按需创建，协调目录可以只是资料入口，源码集成优先安全复用原目标工作区。实际启动及交付时展示聊天标题/ID、资料入口、真实源码 worktree、仓库、工作分支、起点与目标分支的对应表；已有项目路径及旧演练保持原位。完整目录图、映射字段和冲突/接续规则见[工作区目录与聊天、分支对应](.agents/skills/codex-task-coordination/references/worktree-layout.md)。构建、日志及截图产物仍遵守机器和项目约束。

### 开发分支如何建立和收回

实际启动协作时，分别记录各源码仓库当时的当前分支与 HEAD；模块、共享任务从该提交建立各自 worktree。原分支是最终集成目标，可以在模块开发期间正常更新远端代码、接收其他提交，不冻结在启动 SHA，也不默认改为 `main`。

开发中，模块仅按当前审核清单 cherry-pick 明确的共享提交：完整 SHA、用途、改动文件和依赖逐项核对，记录源 SHA → 本地 SHA，不顺带接入其他需求。交付齐备后，所属仓库负责人集中将共享和模块交付 rebase 到原目标分支的最新进度，核验公共改动只保留一份、模块独有提交完整，再快进回同一分支。回写前目标又前进就重新 rebase、复验；临时集成分支通过验证但尚未回写时，仍记待完成。

集成优先安全复用干净且可独占的原目标工作区；需要保留现场、其他任务仍在使用或确需隔离时，才另建候选 worktree。复用原目录也可使用候选分支整批验证后回写；选择条件、两种流程及逐项回写的验收边界见 [集成工作区选择](.agents/skills/codex-task-coordination/references/code-delivery.md#集成工作区选择)。

### 执行、集成与接续中的变化

| 变化 | 处理方式 |
| --- | --- |
| 一个模块后来拆成多个较大模块 | 重评数量与层级，明确范围、核对在途写入并交接后分派 |
| 多个模块本轮只剩一个，或共享任务本轮无工作 | 复用聊天，只等待本轮参与者；不自动归档、不等待空共享交付 |
| 开发中发现共同公共改动 | 确定唯一维护者，完成职责交接后再安排共享开发 |
| iOS 先完成、Android 尚未完成 | 已登记独立本端协调组及冻结范围时，该组依赖齐备后可先集成；若两端同属一个冻结协调组，仍等本组直接参与者齐备，不临时缩小范围；双端联合验收继续等待所需交付 |
| 模块等待共享代码，或设备只支持单任务验证 | 保存阻塞、继续无关工作；必要依赖及时解锁，设备验证排队 |
| 用户在下层追加跨端需求 | 保存原始用户要求，向有权协调层同步并核对修订 |
| 聊天中断、转述未完成或工具不可用 | 对账原聊天、持久消息、待转述及真实 Git，未知结果不直接重做或另派写入者 |
| 目标分支在开发或集成期间继续前进 | 保留新增提交，集成/回写前读取最新 HEAD，rebase 后复验再快进回同一目标；不重开全部任务或退回启动 SHA |
| 模块内部需要临时并行 | 派生子 Agent，由所属模块聊天汇总及统一对外交付 |

消息在本组处理，跨组影响逐层转述；每个真实仓库目标交付线只有一个集成负责人，上层审核冻结清单、规范 SHA 和证据，不重复集成同一目标线。各组分别接续，不把父组一次扫描当成子组已经恢复。

完整协议集中在 [多级独立聊天协调](.agents/skills/codex-task-coordination/references/hierarchical-coordination.md)、[长期接续与需求变更](.agents/skills/codex-task-coordination/references/lifecycle.md) 及 [恢复对账工具](.agents/skills/codex-task-coordination/references/recovery-tool.md)。本说明不复制消息字段或工具命令；工具按组保存、校验和汇总记录，不自动递归调度、执行 Git、后台唤醒或提供文件写保护。

## 模板维护

初始化原稿位于用户级技能 `assets/project-template/`，包括 `resources/` 和隐藏的 `.agents/skills/`；使用技能名称定位，不在项目写死某台机器的用户技能目录。`iOS/AGENTS.md`、`Android/AGENTS.md` 维护双端补充，由根入口明确读取；默认只读源码端 Agent 配置，不给源码端新增索引或配置。

模板更新不会自动覆盖其他 App 的实例；用户主动更新时再合并差异，保留定制、平台维护位置和历史记录。初始化或静态检查通过不代表 App 构建或业务验收通过。
