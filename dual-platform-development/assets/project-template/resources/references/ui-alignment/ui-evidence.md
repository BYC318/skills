# UI 对齐与截图证据流程

## 何时执行、由谁执行

从双端协作入口开展 UI 对齐、Figma 改版、设计还原或接续此类任务时，由主 Agent 读取本流程并维护台账。用户不用再次要求截图。先加载各端真实规则和设计技能；平台已有布局映射、取证和单端报告继续使用，本流程只统一跨端证据身份、四组合覆盖、轮次与验收册。

源码工程师负责所属平台实现、构建、真实导航和采集；主 Agent 核验输入及结果，统一更新台账与验收册。只有主 Agent 写同一份台账；代理可交付独立元数据和图片，禁止并发改台账。源码与协作资料的暂存、提交、推送、发布及外部回写，遵守当前用户授权和项目规则；安装或执行本流程不产生额外授权。

在本协作目录新开任务，根 `AGENTS.md` 会指引读取这里；从独立 Git 源码仓库启动时不假设继承外层规则，应在任务开场显式要求读取双端协作入口。仅保存一份 HTML 演示或依赖旧聊天记忆，不能代替此入口。

仅在用户已主动启用或明确接续 `codex-task-coordination` 时，另读 [独立任务协作技能](../../../.agents/skills/codex-task-coordination/SKILL.md)。公共交付按需 cherry-pick，主任务去重集成，源码来源映射与截图轮次一起记录。消息回执不替代 UI 通过；最终集成后须重建并复验受影响页面，不改写旧截图的构建元数据。

## 范围、优先级和四组合矩阵

- 以本次用户范围为准；整个设计文件先盘点全部业务页面、弹窗及状态，不把示例清单当成文件总量。组件样例、旧稿和不参与项列出排除依据，不静默缩小分母。只有具备完整文件/节点清单依据时才确认盘点完成，文件访问受限时记录缺口，继续明确范围内可做的页面。
- 一个稳定证据 ID 对应一个业务页面的设计状态。空输入、已输入、禁用、选中、校验错误、Toast、键盘、弹窗等设计状态分别登记；同页多个状态复用生产页面，不按 frame 数量生成独立页面。证据 ID 不随排序变化；图片文件名只方便阅读，不作为身份依据。
- 每个状态须留存 **浅色 LTR、浅色 RTL、深色 LTR、深色 RTL** 四种组合。双端默认 8 张实际运行原图；单端明确范围则 4 张。每个组合记录主题、实际有效主题、布局方向、实际有效方向和语言。LTR 使用英语（en）、RTL 使用阿拉伯语（ar），不把设置语言等同于已经证明布局方向。已有项目若明确规定其他语言，更新时保留并列明差异，不能由执行者自行放宽四组合要求。
- 每个组合分别绑定设计节点或有明确依据的适配说明。设计稿未给夜间或 RTL 变体时，仍取运行图并标记“待设计依据”；从已有语义色或镜像规则适配，须记录对应设计 token/项目规范及确认依据。不得拿浅色/LTR 原稿直接判其他组合通过，也不得自行创造视觉标准。
- UI 对齐优先：按明确设计 token、资源和层级实现。新资源来自对应 Figma 设计；可精确参数化的形状和布局仍用原生实现，不把整页原稿截图铺成 App。字体或资源无法取得时记录阻塞，不擅自改用近似图标或占位图。
- 保留已有业务功能。缺失业务能力的入口如何处理，按需求和项目规则执行，不擅自将真实功能改成 Toast（短暂显示的提示）或占位页面；若已授权使用提示占位，记录功能尚未接入。页面可复现所需的选择、输入、校验、键盘和导航须工作；界面通过不代表服务联调通过。
- 页面优先使用当前环境已有的数据。数据不足以展示需要验收的 UI 状态时，允许在 Debug 中填充测试数据或提供状态入口，必须复用实际生产页面和控件，不另做只供截图的假页面。采集信息如实区分 `service`（当前环境实际服务数据）和 `fixture`（包含测试填充的数据）；混用时按 `fixture` 记录并说明哪些内容为测试数据。测试数据可以验证布局、展示和本地交互，不能据此声称真实服务或业务已通过。另走真实产品入口验证导航，生产配置不暴露测试入口；真实业务有副作用时不为截图擅自操作。

## 项目定制与已实现 UI 的接续

开始前核对当前源码、历史任务和设计依据，确认哪些页面已实现、哪些正在重建。本通用流程不要求所有项目先清空旧 UI；项目已明确要求首次替换的，按该项目入口记录范围、阶段、保留依赖和实际 diff，不能仅凭截图或脚本通过认定清理完成。保护业务逻辑、公共组件及其他产品仍使用的代码和资源。

已对齐或重建中的页面继续增量调整。新开聊天、记录缺失、截图过期或缺图都不自动构成重新清空的理由；先核对实际实现，再更新记录和受影响证据。项目的提交授权、功能占位方式和特殊目标验证继续以本项目规则为准，不从其他项目复制。

## 文件分工与开始方式

| 文件/目录 | 用途 |
| --- | --- |
| `任务记录/<任务名称>.md` | 使用既有任务模板记录需求、仓库快照、规则来源、范围、阻塞和下一步 |
| `任务记录/<任务名称>/ui-evidence.json` | 唯一页面台账，包含四组合设计映射、预期构建、全部取证轮次和审查记录 |
| 外部任务证据目录 | 原始截图、布局记录、资源清单快照、比较图、`验收册.html` 与 `校验结果.json` |

外部目录由当前项目说明、用户和机器规则确定；不写死个人盘符。执行前核对目录存在、存储可用，且位于协作目录和实际源码仓库之外，指定存储不可用时停止，不自行回退。CLI 显式接受已经存在的外部目录，自动拒绝协作目录内的证据根；实际源码仓库位置仍由 Agent 核对。台账内记录本次实际路径用于接续，不写回通用原稿。

下列命令从协作根目录执行；`证据根` 是已核对并创建好的本次专属外部目录。初始化不覆盖同名任务。脚本只依赖 Python 3 标准库，不负责登录、启动设备或伪造 App 截图。当前构建记录要求实际完整 Git 提交 ID 及源码、产物 SHA256，正式截图交付适用于已绑定且使用 Git 的参与端；非 Git 工程可使用协作入口，但该工具的构建身份尚不支持，不编造提交 ID 使检查通过。

```bash
python3 resources/scripts/ui-alignment/ui_evidence.py init \
  --name '任务名称' --scope '本次页面范围和设计链接' --evidence-root '证据根'
```

每次新增、绑定、取证、审查和失效操作成功后，脚本自动刷新验收册与校验结果；任务说明里的阻塞和下一步仍由主 Agent 更新。新任务如果存在同名台账，应恢复而非再次初始化。

## 设计登记与基准

先保存真实原稿、导出的资源及资源映射；版本号只是追溯方式之一。版本可用时传入锁定参数；Kothar 使用 `figma_url` 时把 `version-id` 放进 URL，不能同时给无版本 URL 和单独 `version_id` 并假设后者生效。版本不可得时，用保存的原稿 SHA256、资源清单快照和设计节点形成明确基准；`unknown` 本身不构成失败。

下面仅为命令格式，不把示例值当成真实节点；用任务中实际核对的信息填写。`state-id` 是稳定机器标识，`state` 是中文展示名。

```bash
python3 resources/scripts/ui-alignment/ui_evidence.py add-page '页面台账.json' \
  --page 'login-password-empty' --module '手机号登录' --title '输入密码' \
  --state-id 'empty' --state '未输入' --locale 'en' --baseline 'B001' \
  --file-key '实际文件key' --node-id '实际节点ID' --theme light --direction ltr
```

此命令只绑定实际提供的一个组合，其余三个组合明确待绑定。用 `bind-reference` 分别绑定；必要时 `--version-id` 指定设计文件版本。`basis-note` 填真实设计变体说明，或已确认的 token/适配依据。不能为了填齐矩阵自动复制同一张浅色原稿冒充四种设计。

```bash
python3 resources/scripts/ui-alignment/ui_evidence.py bind-reference '页面台账.json' \
  --page 'login-password-empty' --variant dark-rtl --locale ar --baseline 'B001' \
  --file-key '实际文件key' --node-id '实际节点ID' --basis-note '实际深色 RTL 稿或明确的已确认适配依据'
```

完成真实范围盘点后运行 `inventory <台账> --basis '完整文件/节点清单的可追溯位置及范围依据'`。新增状态会自动撤销“盘点完成”，需要重新确认。没有登记页面、没有盘点依据或只是示例的台账，不能判定全量完成。

## 构建、采集与轮次

截图优先使用 iOS 模拟器或 Android 模拟器，暂不要求真机截图；没有真机不构成 UI 取证缺项。先运行本次 App 构建并进入对应生产页面，再采集实际运行原图，不得用设计稿、绘制或拼接的图片冒充 App 运行证据。页面使用测试数据不影响运行截图作为 UI 证据，但截图必须确实来自 App。工具自动检查中直接生成的小图片仅用于测试工具本身，不能作为页面验收证据。收尾按批取证，保留四组合要求，不为每次小改动反复截图。

1. 核对两端当前 Git、工作区、实际工程、工具会话和设备，读取目标目录新增规则；按平台规则补齐构建产物路径；公共层变化按实际消费者和关联目标安排验证。共享主机上的大构建和设备操作串行，避免取错应用或设备。
2. 在授权范围实现；源码提交按用户授权和本项目规则执行，不能从截图流程推导提交权限。替换资源后检查静态引用、动态加载、工程/Bundle、各变体、共享模块和关联产品；只删除能够证明已无用途的旧资源，记录保留原因。资源清理不扩大为全仓库清理。
3. 收尾使用同一批次可运行产物采集四组合，不在每个小改动后反复全量构建。生成构建清单 JSON：参与平台各一份 `{commit, worktree_digest, artifact_sha256}`，完整 Git commit、源码工作区指纹和实际 `.app`/APK 产物 SHA256 都须来自实际命令。工作区指纹覆盖本次源文件差异及未跟踪代码，`.app` 目录可用排序后的文件路径及逐文件哈希生成整体指纹；不得用 commit 代替脏工作区或复用陈旧包。
4. `round <台账> --page <ID> --builds <构建清单.json>` 创建 `R0001` 等新轮次，并冻结本轮页面身份、四组合基准和预期构建。后续重拍创建新轮次；历史原图和审查记录不覆盖。
5. 正常导航或 Debug 固定状态进入页面；核验前台应用、至少两个该状态独有的可见锚点、内容、滚动、焦点、键盘、语言、实际主题和布局方向。连续观察/截图确认布局稳定；设计有 Toast 状态时另留可见反馈图及触发记录。
6. 平台截图工具保存原始 PNG 及布局/无障碍树或采集日志。原始截图不得涂改、裁切或合成；身份不符先重新导航取证，不据此修复代码。服务数据不足时按上述规则使用测试数据继续 UI 取证，并记录真实服务尚未验证；无法运行 App、进入目标页面或采集截图时才如实记录相应取证阻塞，不能用设计稿、生成图片或另一端截图替代。

每个组合依次登记 `figma`、`ios`、`android`；单端任务只登记参与端。目录自动包含 **证据 ID / 基准 / 轮次 / 主题-方向 / 平台**，同名截图不能互相覆盖。

源码实现、构建或提交完成不等于页面验收通过；尚未采集四组合时保留待截图或需复验状态。任务记录关联源码状态、页面 ID 和证据轮次；构建元数据保持采集时的真实来源，提交后不直接改写其中的 commit 冒充重新构建。差异修正后另建证据轮次，源码和协作资料的提交继续遵守实际授权。

```bash
python3 resources/scripts/ui-alignment/ui_evidence.py attach '页面台账.json' \
  --page '页面ID' --variant light-ltr --platform ios \
  --image '实际原始截图.png' --metadata '实际采集信息.json'
```

### 采集信息契约

所有 JSON 数据均由实际采集结果填入，不从示例复制成“已验证”。共同字段：

- `page_id`、`state_id`、`baseline_id`、`theme`（`light/dark`）、`direction`（`ltr/rtl`）、`locale`，必须与对应组合完全匹配。
- `captured_at`：包含时区的 ISO 时间。
- 原稿另记录 `file_key`、规范化冒号形式 `node_id`、可用时的 `version_id`；`resources_manifest_path` 指向本次设计资源来源/格式/倍率/哈希和两端目标资源映射的清单。没有图片资源也记录其不适用依据。

运行图另记录：

```json
{
  "page_id": "页面ID", "state_id": "状态ID", "baseline_id": "B001",
  "theme": "dark", "effective_theme": "dark", "direction": "rtl", "effective_direction": "rtl", "locale": "ar",
  "captured_at": "实际带时区时间",
  "application_id": "实际应用ID", "foreground_application_id": "实际前台应用ID", "route": "实际入口和状态路径",
  "data_source": "fixture", "debug_only": true, "normal_entry_verified": true,
  "raw_screenshot": true, "identity_verified": true, "stability_verified": true,
  "anchors": ["实际核验锚点一", "实际核验锚点二"],
  "device": {"alias": "匿名设备别名", "os": "实际系统版本", "orientation": "portrait", "width": 0, "height": 0, "scale": 0},
  "build": {"commit": "实际完整提交ID", "worktree_digest": "实际源码指纹", "artifact_sha256": "实际产物指纹"},
  "layout_path": "本次布局树或采集日志路径"
}
```

示例的 `0` 和文字占位必须替换，脚本会拒绝。`device.width/height` 是原始截图像素，`scale` 是实际显示密度。真实服务状态使用 `service`，不把 `fixture` 的 UI 结果写成服务通过。新采集记录的 `device.alias` 明确注明真机、iOS 模拟器或 Android 模拟器及机型，`device.os` 记录实际系统版本；使用匿名别名，不记录设备唯一标识。交付说明注明截图来自哪个平台的模拟器或真机，以及页面使用已有环境数据还是测试填充数据；模拟器为正常取证方式，无需因没有真机额外列为阻塞。不在报告记录密码、Token、真实手机号和其他敏感资料。

需要裁切、统一内容区域或缩放进行比较时，在元数据增加 `comparison_image_path` 和明确的 `comparison_transform`（原始区域、目标逻辑尺寸、安全区、排除区域）；派生图另存 `comparison.png`，原图仍保留。报告禁止将不同比例的图片硬拉伸叠加。

## 审查、失效与验收册

每个主题和方向组合分别实际审查：布局、图片、字体、交互、缺失功能 Toast、旧资源清理和证据身份。系统键盘/状态栏、字体光栅化等差异逐项记录依据，不用“系统差异”笼统豁免，不编造相似度或质量分。所有未处理问题列入 `open_issues`。

`review <台账> --page <ID> --variant dark-rtl --review <实际审查.json>` 留存审查者、带时区审查时间和全部检查项：

```json
{
  "reviewer": "实际审查者", "reviewed_at": "实际带时区时间", "open_issues": [],
  "checks": {
    "layout": {"status": "pass", "note": "实际核对依据"},
    "images": {"status": "pass", "note": "实际核对依据"},
    "fonts": {"status": "pass", "note": "实际核对依据"},
    "interaction": {"status": "pass", "note": "实际操作和结果"},
    "toast": {"status": "pass", "note": "实际触发与本地化提示记录"},
    "resource_cleanup": {"status": "pass", "note": "实际替换、删除或保留依据"},
    "identity": {"status": "pass", "note": "实际前台应用、状态、主题与方向核验依据"}
  }
}
```

这是格式示例，不是现成通过记录；实际有差异使用 `fail` 并列出问题。只有 `toast`（没有缺失功能）和 `resource_cleanup`（没有替换资源）可有依据地填 `not_applicable`；不允许四组合整体“不适用”。脚本校验元数据、文件和覆盖关系，**无法从截图自动证明文字填写真实，也无法替代视觉与业务审查**。

更新规则：

- 改动设计基准、共享组件、主题、方向、资源或业务状态后，立即 `invalidate <台账> --page <ID> --reason '实际原因与影响'` 标记受影响页面待复验，然后构建、新轮次取证。变更影响不明确时不能继续沿用旧通过记录。仅声明“无影响”而没有检查依据不能复用旧截图。
- 一轮的同一组合、同一平台原图只登记一次；失败轮次也保留。修正后新建轮次，`current_round` 选择当前一轮，不能静默切回旧图掩盖失败。中断时当前轮次可不完整，报告如实展示缺图。
- 设计依据缺失为“待设计依据”；缺图为“待截图”；元数据/文件不符为“证据无效”；差异未处理为“有差异”；图片齐全但未审查为“待验收”；已失效为“需复验”。**每个组合所有参与端齐备并通过审查，且四组合都通过，才算页面完成**。
- 完成一批、重拍、状态变化、中断和交付前运行以下命令。未完成可以生成报告，但全量完成检查必须失败，禁止将空台账或未盘点完视为 100%。

```bash
python3 resources/scripts/ui-alignment/ui_evidence.py check '页面台账.json'
python3 resources/scripts/ui-alignment/ui_evidence.py render '页面台账.json'
# 诊断全量证据是否齐备；正式完成声明还须执行下节的 deliver：
python3 resources/scripts/ui-alignment/ui_evidence.py check '页面台账.json' --require-complete
```

`check` 普通模式检查记录问题，返回 0 不代表 UI 已完成；`--require-complete` 另外要求盘点完成、非空范围及所有页面四组合通过。验收册可离线打开，支持模块/状态搜索、四组合切换、并排/叠加、原图放大、证据详情和历史轮次。验收册与校验 JSON 都可重建，台账和原始证据才是接续来源。

交付时给出实际台账和验收册路径，已登记/盘点状态、8 图覆盖与四组合通过数、差异/失效/阻塞、Toast 功能占位和旧资源清理结果；分别说明构建、运行、UI 和真实服务证据。不要把之前聊天的演示数据导入正式台账。

## 统一交付检查与回执核验

声明本任务 UI 全量完成前，先核对当前源码、实际构建、Figma 基准与台账一致，对受影响证据执行失效和复验，并实际审查截图及源码差异。之后运行统一入口，不能仅用聊天完成声明、旧 HTML 或普通 `check` 成功代替：

```bash
python3 resources/scripts/ui-alignment/ui_evidence.py deliver '页面台账.json'
```

`deliver` 复用完整验收检查并刷新报告。退出码 0 且输出 `completion_allowed: true` 时，在外部任务证据目录的 `deliveries/<交付ID>/` 下生成独立的 `交付回执.json`、`台账快照.json`、`校验结果.json` 和 `验收册.html`。回执绑定台账绝对路径与 SHA256、当前页面轮次、四组合审查者及审查记录摘要、检查结果与归档文件哈希；原始证据仍保留在本任务目录，不复制或改写原图。重复交付另建归档，保留旧回执。缺项时退出码 1，输出 `completion_allowed: false` 和具体缺口，不发布通过回执；输入错误或收尾期间台账、证据变化时退出码 2。失败时如实报告待取证、待验收或阻塞。

接续、上级验收或再次引用完成结论时，对实际回执路径执行：

```bash
python3 resources/scripts/ui-alignment/ui_evidence.py verify-delivery '页面台账.json' \
  --receipt '实际证据根/deliveries/实际交付ID/交付回执.json'
```

复核只读检查当前台账、当前原图和辅助记录、归档文件及审查绑定，不信任回执里的通过标记。台账任何更新、设计或构建变化、新轮次、截图缺失或哈希不符、审查记录缺失，都不能沿用旧回执。台账更新后重新执行 `deliver`；涉及设计、构建或实现变化时先复验，不能只重新签发。各层协调者按职责核对参与者证据，不把某个模块的回执当成全需求完成。

最终 UI 完成说明必须附当前台账、本轮交付回执、归档验收册路径和本次命令结果，注明范围盘点、四组合及参与平台覆盖、未解决问题和业务验证边界；任务记录保存同样入口。中途汇报和已授权的源码提交继续按原规则执行，无需每个小改动都生成交付回执。

该检查由 Agent 在收尾时主动运行，不安装自动结束检查，也不在每轮对话后自动运行；未运行或复核失败时，执行者及协调者不得声明 UI 全量完成。回执提供可核对的文件与审查记录关联，无法自动证明审查文字真实、实时设计未变化或当前源码未变；实际视觉与业务判断仍由执行者和验收者负责，源码清理也继续核对实际 diff。
