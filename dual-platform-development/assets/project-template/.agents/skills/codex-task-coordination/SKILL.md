# 独立 Codex 任务协作

跨聊天执行仅在用户主动点名 `$codex-task-coordination`、明确要求采用该模式或明确继续已启用任务时启动。规划咨询按下节只读协议，不等于启动；普通开发、UI 对齐或已有目录不自动启用。本轮内已明确启用后，正常接续无需重复点名。仅讨论、修改技能不创建真实任务。

这是可独立复用的任务协作技能。通信、恢复和交付协议保存在本目录；工程路径、项目授权、平台规则和验收方式由调用项目提供，不依赖相邻技能或特定 App。复用及配置契约见 [项目接入](references/project-configuration.md)。

用户主动使用本技能处理开发需求，表示需求较大且希望通过并行缩短整体交付周期。默认按完整业务需求组织多个独立任务，先归拢同一业务流程、状态和验收，再核对可并行边界；不把“一端一个执行任务”作为默认终局，也不为增加数量拆散同一需求。实际创建、调度与源码操作仍遵守本次授权；只读规划不自动启动。

## 只读规划与实际启动

用户在双端工作流中询问任务安排、任务数量、进度预估、角色职责，或要求检查是否按本协议规划时，先只读本节、启用价值评估及 [按工作量选择层级](references/hierarchical-coordination.md#按工作量选择层级)，结合项目配置给出方案；无需用户先记住技能名。这里只读取规划依据，不表示启用跨聊天执行，不创建聊天、worktree、批次或消息，也不运行恢复/通知工具。

- 默认规划的是 Codex 独立任务和聊天，不是真人招聘或人员配置。先列可独立实现并验收的模块、源码边界及公共依赖，再决定模块数量、是否需要端内协调、共享任务及同时推进的数量。协调任务不计入编码能力，不固定按一端一个执行者，也不为了层级完整增加空角色。
- 方案写清任务角色、范围、依赖、交付证据，以及哪些可同时推进、哪些须等待。已有实现、构建条件或样板耗时未核实时，列为估时假设；先给阶段与待核对项，不把真人“人周”直接换成 Codex 工期，也不只按设计状态数量承诺日历周期。用户明确询问真人团队时，另列人员假设，不与聊天数量混用。
- 用户指出偏离时，暂停沿用受影响的分工结论，重读对应规则与最新纠正，再修订整份方案。说明哪些来自规则、哪些是本次推断，不只改角色名称或凭印象声称“技能规定”。已有在途任务仍按恢复和交接规则核对，不能通过规划说明直接改变其归属。

规划、分工、调整、进度汇总及阶段/整体交付的每轮最终回复，都按 [每轮回复的任务结构图](references/hierarchical-coordination.md#每轮回复的任务结构图) 展示最新完整层级；节点从规划阶段就写完整拟用聊天标题，区分候选与已创建，不能等创建后才命名或只展示变化部分。

实际启动、创建或调度独立聊天，仍须满足下文“开始与授权”。普通开发不会仅因本节自动采用跨聊天模式；已有明确授权不重复询问。

默认让本批已授权、职责和源码边界明确的全部执行任务并行启动。缺依赖时记录 TODO 并持续推进本任务可做部分，只让依赖对应的接入和验证等待；构建、设备和同工作区 Git 操作仍分别排队。工具并发硬限制或实际资源不足时说明真实限制及排队任务，尽量用满可用容量，不假报全部正在运行。具体执行按 [缺依赖时持续推进](references/hierarchical-coordination.md#缺依赖时持续推进)，TODO 不代表真实接入或验收通过。

## 启用价值评估

先只读项目配置、实际需求和已有任务资料。用户已主动选择本技能时，评估重点是怎样在保持需求完整、质量和授权边界的前提下缩短交付周期，而不是再次默认退回单任务。按 [按工作量选择层级](references/hierarchical-coordination.md#按工作量选择层级) 比较集中执行与按业务模块并行，既检查通信、集成和返工成本，也检查集中执行造成的排队与等待；调用技能本身不代替创建聊天或执行操作的授权。

- 仅只读咨询、局部小改动，或已核实需求只有一个不可合理拆分的执行单元时，可以当前聊天完成或复用原任务，说明依据。不能只凭“尚未盘点”“可能冲突”“先保守一点”将较大需求长期压成每端一个任务；先补查边界，将启动试跑与后续模块并行分别安排。
- 先按业务目标归组：同一平台内同一业务的相关页面、交互、状态、异常处理和验收由同一个长期模块任务负责，追加同类需求优先回到原任务。不同完整业务在源码边界和接口明确后并行；两端仍按平台分别实现，不将跨端同一需求混成同一源码写入任务。数量由实际归组和依赖决定，不固定每端一、二或三个。
- 若全局只有一个执行单元，通常由当前聊天直接实现，不额外设置“协调主任务＋一个执行任务”。用户明确要求保留独立模块窗口，或已有长期聊天承担明确接续职责时，可以轻量复用，并说明其具体价值；不为了满足数量创造共享任务或空协调层。iOS、Android 各一个可独立推进的任务时，全局已有两个执行单元，仍可能适合独立聊天协作，由双端协调聊天直接协调，不另建端内协调聊天。两端源码独立且不存在共同公共来源时，不启动端内共享任务，本端公共代码调整归对应模块执行；若两端确实共同修改同仓库同一份代码，仍按真实消费者由共同上级协调唯一的仓库内共享维护者。跨仓库真实公共依赖按其自身条件判断，已有维护归属仍遵守恢复与交接规则。
- 对已启用的协作先恢复原聊天、依赖和在途动作；本轮参与者变少不自动撤销原分工、接管源码或归档聊天。确需简化结构时，按 [结构调整与接续](references/hierarchical-coordination.md#分层接续与结构调整) 完成交接后再调整。

创建或扩大任务前，列出完整业务分组、各端任务归属与数量、必要协调/共享角色、可写范围、依赖和验收。分别给出启动阶段、正式开发的参与任务、编码并发与构建/截图容量；说明比集中执行减少了哪些等待，仍需串行的部分及具体原因。未核实处标为候选并补查，不承诺固定数量或无依据的工期。任务数量的判断见 [按工作量选择层级](references/hierarchical-coordination.md#按工作量选择层级)。实际采用独立聊天时，把结论记入批次 `collaboration_assessment`；不采用时只在当前聊天说明，无需创建空批次或长期目录。用户已经授权的合理分工自主执行，不为评估增加逐次确认；用户明确指定组织方式时遵守，不用默认建议代替其选择。该评估由 Agent 完成，不是消息脚本的自动评分或调度能力。

## 跨聊天推进与任务内执行

本技能管理较大需求在独立任务窗口中的长期推进：真实聊天身份、模块归属、需求修订、批次、跨聊天通信、交付和恢复。它不决定每个聊天内部必须由一个 Agent 完成，也不禁止派生子 Agent。

双端项目统一使用“双端协调、端内协调、模块执行”区分角色。`main` 指本组协调者，`worker` 指模块执行或父组中的子组协调者，`shared` 指按需设置的共享维护者；这些角色不等于每个聊天内部的主 Agent。

双端总协调和端内总协调是专职协调角色，只负责拆分、分派、依赖沟通、只读审查、证据核对、协作资料及已授权的 Git 集成，不承担业务代码、公共代码、工程引用或源码冲突修复。不能通过给自己预留模块、临时改称执行者或在协调聊天内派生编码子 Agent 绕过分工；需要改源码时交给模块或按需设置的共享任务。单 Agent 独立开发及模块、共享任务内部主 Agent 仍可在自身授权范围直接实现、修复、构建和验证，也可按需派生子 Agent。调整已分配源码前先核对在途动作和工作区，确认原执行者停止相关写入并记录交接；执行者不可用时保留阻塞或按授权重新分派，不由总协调代写。获授权的 Git 集成可以改变工作树，但需要人工改源码的冲突交回执行者；同一工作区操作仍串行。

子 Agent 属于所在独立任务的内部执行者，不是新的长期独立聊天。其标识不替代真实聊天 ID，也不另占长期目录的模块身份；所属独立任务负责汇总结果、按授权发布对外消息与交付，保留可接续资料。公共代码的唯一维护归属以独立任务为单位，任务内部委派不转移归属；内部仍须协调文件写入、Git 状态和共享设备，避免并发冲突。恢复依靠所属聊天及落盘记录；重新派生前核对之前的子 Agent 当前状态、实际改动和在途写入。聊天中断、上下文压缩或缺少最新汇报均不证明原执行者已停止；状态不明时保留待核对，不直接给同一源码范围再安排写入者，其他独立工作可继续。确认需要替换时先停止或交接原写入职责，再派生新执行者并记录关系。

## 按需启用多级独立聊天

可按工作量采用“双端协调聊天 → 端内协调聊天 → 模块执行聊天及按需共享聊天”，必要时增加真实跨仓库公共依赖任务；允许省略协调层，两端层级也可不同。每个协调组独立维护批次和唯一 main，端内协调聊天可同时作为父组 worker 和子组 main。模块和共享聊天内部可直接开发或派生子 Agent；总协调聊天内部仅处理协调、只读核对和已授权集成。

采用多级结构，或调整既有层级时，读取 [多级独立聊天协调](references/hierarchical-coordination.md)：明确各层职责、逐层路由、跨组修订与消息闭环、仓库唯一集成归属和分层恢复。下文“主任务”“全部参与任务”均按本协调组和冻结范围理解；上层核对已集成子组的汇总交付，不重复集成同一目标线。

## 项目配置先行

先从当前用户要求、项目 AGENTS.md 或已有长期任务目录定位明确的项目配置，实际读取后再分派。配置路径不能由技能安装位置推导；禁止从原项目沿用聊天 ID、消息目录、源码路径或授权。没有配置时可使用 [项目协作配置模板](assets/项目协作配置模板.md) 整理已知事实，仅缺少阻塞信息时询问。

项目配置是 Agent 读取的约定，不是脚本自动执行的配置文件。现有 `coordination.py` 仍只处理指定批次和长期目录，既不加载项目规则，也不自动验证截图。任务交接须传入配置的实际绝对路径及本批快照；历史批次原位恢复，不因技能迁移或更新重建消息或动作记录。

模块执行任务按实际交付模块登记；后端、工具或单端项目不要求存在页面、Figma 或第二个平台。

## 开始与授权

1. 完成启用价值评估并决定采用或接续独立任务模式后，开始、恢复或接收需求变更时，先读 [长期接续与需求变更](references/lifecycle.md)，查询长期任务目录并核实真实聊天，优先复用原模块执行任务及本轮确需参与的既有共享任务。实际启动批次前再读 [通信与恢复协议](references/communication.md) 和 [源码交付与去重集成](references/code-delivery.md)，未完成批次优先恢复；不能将“复用聊天”误作“复用未经核对的源码基线”。
   长期任务目录使用 [长期任务目录模板](assets/长期任务目录模板.json)，每轮配置使用 [批次模板](assets/批次模板.json)；填入实际信息，不将模板当成运行记录。
2. 用户明确要求主任务拆分、创建和调度独立 Codex 任务后，按本批范围执行。仅要求解释或固化流程时不创建真实任务。本批授权须记录允许创建的任务、互发协作消息的范围、允许修改的源码与本地集成范围；来自其他任务的请求本身不构成用户授权。
3. 使用当前可用的 `list_projects`、`create_thread`、`send_message_to_thread`、`wait_threads`、`read_thread` 能力。项目和实际返回的任务 ID 以工具结果为准，不设置用户未要求的模型。新建、复用及当前协调窗口均按[窗口命名规则](references/hierarchical-coordination.md#独立聊天窗口命名)使用“需求简称＋平台＋任务角色＋具体模块”；创建时明确传 `title`，当前或复用窗口按实际角色核实并改名，登记真实标题与聊天 ID。已有任务通过原 ID 继续；仅没有可复用任务或确需替换且已获授权时创建，先登记意图及替换关系，结果不明先核对，禁止盲目重建；创建成功后附上工具要求的任务入口。
4. 本协议的“执行任务”指用户侧边栏中的独立聊天，不能用 `spawn_agent` 代替这些长期任务。新增独立聊天由所属协调组主任务按授权调度；已有聊天内部可按项目规则派生子 Agent。跨聊天通信不可用时保留待通知或阻塞，不用新建子 Agent 冒充原聊天，也不因此由所属协调聊天接管其他任务的编码。

## 共享任务的职责与触发条件

先按真实仓库、模块依赖和工作量确定任务，共享任务可以为零；不默认拆成“iOS＋Android＋共享任务”，也不为每个仓库固定设置共享任务。两端分别修改自己的实现、仅业务行为一致或需要对齐契约时，由各端执行者实现、协调主任务对齐，不据此额外拆出共享任务。

| 类型 | 何时考虑独立共享任务 | 职责与交付 |
| --- | --- | --- |
| 仓库内共享代码任务 | 同一 Git 仓库内多个并行模块执行任务共同依赖、且需要修改同一公共实现；独立维护能避免重复开发或并发修改 | 在该仓库的独立 worktree 唯一维护明确的公共代码、资源、API、工程引用及必要测试；审核后由消费者在同仓库各自 worktree 按清单 `cherry-pick -x`，集中 rebase 时公共改动只保留一份规范结果 |
| 跨仓库公共依赖任务 | 多个仓库确实消费同一权威来源，且本轮需要统一修改或发布该来源，例如公共协议、共享 SDK 或共享源码仓库 | 唯一维护公共来源及其接口、兼容性、版本和验证，明确各消费者；按已核实的依赖机制交付，各端适配和本仓库接入改动仍归对应执行者，不强制跨仓库挑选同一份源码提交 |

分派前登记类型、触发依据、权威来源的真实 Git 根与路径、唯一维护者、消费者和接入方式；同名文件、相似组件或两份平台实现不是同一公共来源。跨仓库依赖须核对其真实维护仓库，子模块路径不改变源文件归属；不能从任务名称推导新的仓库访问或源码修改授权。

只有一个消费者且没有独立公共来源维护需要时，优先由所属模块完成，不为演练协议拆出共享层。已有共享维护归属和运行记录继续保留；本轮无共享改动时不将其加入等待条件，也不因新默认擅自转移源码、归档聊天或删除在途依赖。已决定使用的共享任务可按需求顺序维护，不要求每个组件另建聊天；每个公共路径始终只有一个写入方。

两类任务沿用现有 `shared` 协议角色，逻辑 ID 按实际归属区分；角色名和模板示例不是固定任务数量。提交接入与公共依赖交付的不同记录方式见 [源码交付与去重集成](references/code-delivery.md)。

分派、职责交接、目标/范围/验收实质变化及完成判定时，按 [任务目标与分派责任链](references/task-traceability.md) 传递原始目标和本层分派，核对需求到负责人及证据的覆盖；拆层不转移上级对所属交付的责任。

## 分工与隔离

- 主任务盘点设计及已有代码，拆分有实际独立性的页面/模块，维护批次配置、需求目录、发布清单、去重集成记录和统一 UI 台账。任务数量按真实工作和设备容量决定，不按每个页面或每个组件机械创建任务。
- 协调主任务负责调度、已授权的 Git 集成、只读审查和证据核对，不接管已分配给模块或共享任务的源码。业务、公共代码及其工程引用由指定维护者实现，执行任务内部主 Agent 可直接编码、构建、测试和取证，也可委派子 Agent。冲突或验收失败涉及已分配源码时，交回所属执行者或完成职责交接后重新分配，不能以“集成修复”为由直接接管。
- 共享任务按上述触发条件承担已登记公共路径或公共依赖的唯一维护职责；先检查已有能力，按真实仓库和消费者明确范围，不按平台名称凑角色。
- 模块执行任务只修改分配的模块范围，调用公共组件，缺能力通过主任务提需求，不在页面目录复制替代组件。公共路径及共享工程配置的归属在批次中列明；这是协作规则及集成检查，不能声称 worktree 自动提供文件写权限隔离。
- 每个源码仓库实际启动时记录当前分支为最终目标、当时 HEAD 为开发起点，各模块及仓库内共享任务从该起点创建独立 worktree 和分支。目标分支可正常持续推进，最终交付 rebase 到它的最新状态并快进回写，详见 [分支基线与集成规则](references/code-delivery.md#启动分支开发基线与-worktree)。同一 worktree 的 Git 状态操作串行；集成优先安全复用原目标工作区，候选 worktree 按需隔离，选择条件和两种流程见[集成工作区选择](references/code-delivery.md#集成工作区选择)，最终回写仍核对目标工作区。存在多个或嵌套 Git 根时分别隔离，外层 worktree 不会自动隔离内层源码。子模块也要核对实际工作区，不能经软链接共享活动源码。
- 源码工作区按[目录与聊天、分支对应规则](references/worktree-layout.md)组织，默认在原源码仓库所在父目录下建立与仓库并列的 `worktree/<需求简称>/<平台>/<任务目录>/`，按实际源码位置确定根；共享角色按需建立，协调工作区优先安全复用。登记并展示真实聊天、资料入口、实际源码 worktree、仓库及工作/目标分支，不能把普通目录或未绑定环境当成已隔离源码。
- 每个执行任务收到项目配置、真实源码 worktree、Git 根/分支/基线、需求 ID、可写与只调用路径、源码逐级规则、所需技能、产物路径、消息目录、依赖及验收项。UI 任务另外传入设计节点、页面状态及平台补充；非 UI 任务使用其契约与验收依据。独立聊天不自动继承主任务上下文。

## 执行闭环

1. 主任务核对长期任务目录，绑定本轮参与的既有聊天及职责，再建立批次配置和任务记录；确需新任务才登记创建意图与真实 ID。执行任务先核对身份、原始用户授权及需求修订，读取协议，确认接单再编码。
2. 常用分派、接单、交付、阻塞、就绪与关闭优先用[消息操作封装](references/message-operations.md)，复用原校验并推导身份、引用和实际产物哈希；理解、授权及验收仍由所属聊天负责。实际通知必须使用[受控调用器](references/notification-gate.md)，核对消息、当前修订与真实绑定，持久领取本次发送并保存实际回执；异步命令只接续原会话。前置失败不发送，未知结果不直接重发。本组主任务与直接参与任务通信，执行任务与共享任务经本组主任务路由；跨组由兼任上下层角色的协调聊天转述。接收与理解分别确认，重复通知不重复执行。
3. 本批存在共享任务时，按其类型交付公共提交或依赖版本。主任务核对来源、API、设计及验证后发布 READY；仓库内消费者按需 `cherry-pick -x` 并记录 SHA 映射，跨仓库消费者按已核实的依赖机制接入并记录来源版本与本仓库提交。无关历史不带入，公共维护与消费者改动分开，细节遵循 [交付方式](references/code-delivery.md#按共享类型选择交付方式)。
4. 默认等本次约定范围内全部参与执行任务终版交付齐备、本批实际存在的共享交付已封版且无未解决依赖后，主任务再开始集中集成。单个任务先完成只收存交付，不因每次 commit 或进度上报提前纳入最终集成，不擅自缩小范围规避等待。源码及时原子提交与集中集成是不同节奏。
5. 集中集成由所属仓库唯一负责人执行，优先安全复用原目标工作区，需要隔离时才另建候选 worktree：先把共享交付、再把各模块独有交付依次 rebase 到启动时记录目标分支的最新进度，逐项核验并排除已被规范公共结果覆盖的消费副本，保留原子提交与旧/新 SHA 映射。回写前目标若继续前进，再 rebase 并复验，最终快进回该分支；不以协调者 cherry-pick 模块提交替代 rebase，不 reset 或改写目标既有历史。跨仓库公共来源与消费者接入提交分别在所属仓库处理。具体去重、冲突归属、异步中断及回写完成条件见 [源码交付规则](references/code-delivery.md#模块交付与协调去重)。 集中集成前按[执行资料防护](references/execution-guards.md)调用 `freeze-integration` 登记快照及冻结状态，以 `check-integration` 核验后继续；源码提交前用 `check-staged` 按原始路径核对暂存范围。 分支切换及关键步骤前后用 `switch-candidate`／`check-candidate` 核对实际候选或目标分支与累积提交，本地脚本序列用 `run-scripts` 预检绝对路径并在失败时停止后续步骤。
6. 开发期间仅对共享依赖、阻塞、契约/范围变化及最终交付发送必要通知，不按每次提交、普通进度或每张截图唤醒主任务。可合并的非紧急需求整理后一次提出；ACK/回执可随同一次必要通知交付，不为每条状态单开一轮对话。模块执行任务之间不互相广播普通进度。
7. 缺依赖先登记可追踪 TODO/依赖请求，持续完成本任务不受影响的实现与验证；只有当前可独立推进的工作全部做完后，才保存进度、写剩余 `BLOCKED` 并结束本轮。主任务运行时用有界 `wait_threads` 收集结果，再通知继续，不依赖无限 sleep、持续自发回复或隐含后台唤醒。先完成任务只交终版清单后等待，不反复修改已冻结交付；修订须明确递增并通知受影响者。
8. 执行项目配置指定的验收流程。UI 任务必须读取配置绑定的截图规则、证据工具及验收册入口，按配置矩阵取证；非 UI 任务按其测试、构建或交付证据验收，不虚设截图要求。共享设备取证排队；执行任务提交元数据，主任务统一收录台账。集中集成后安排执行者重建并复验受影响范围，保留旧轮次及真实来源，不能把源 worktree 证据改名冒充集成构建证据。配置要求的验收能力缺失时保留待验证，不降低通过条件。

## 完成与接续

本轮已验收不等于长期模块执行任务终止。交付后保存下一步与恢复入口，任务转为“等待下一轮”；只有用户要求或确认替换时才归档。追加需求复用原聊天，按 [长期接续流程](references/lifecycle.md) 选择当前批次修订或下一批次；每批仅等待本批参与者的冻结范围。

中断、纠正方向或长时间追加讨论后，恢复前执行 [恢复对账](references/lifecycle.md#中断与反复纠正后的恢复对账)：补录检查点之后的最新用户要求，逐项核对未关闭依赖及真实执行结果，为旧请求明确保留、修订或取消。主任务与执行任务均适用；不能把“聊天后来没再提”当作请求已取消，也不能把暂停一个任务当作其他任务已停工。恢复摘要写清已完成、仍等待谁、已变更/撤回及下一动作，核对清楚后自主继续，不要求用户机械确认每次摘要。

开始、恢复及完成判定前，按 [恢复对账工具](references/recovery-tool.md) 运行 `recover`，有长期目录时优先 `--registry` 扫描所有登记批次，否则用 `--root` 核对本批。读取未完成请求、待确认消息、执行与通知调用结果未知项及下一步；跨批 `scan_complete=false` 不得声称对账完成。同仓库 `cherry-pick` 接入前后运行 `begin-action` / `finish-action` 留下意图与回执；rebase、目标回写及其他依赖接入按 [交付方式](references/code-delivery.md#按共享类型选择交付方式) 保存意图与结果。未知结果先核对实际状态，不直接重做；依赖核验完成后由主任务发布结构化 RESOLVED，不能用 ACK 或完成文字代替。

普通接收确认使用幂等 `ack` 入口，ACK/ACCEPTED本身不再确认；自主理解的ACCEPTED仍由接收者编写。消息的 `ACK` 仅证明收到，不证明代码执行成功。需求就绪、消费者接入、源码集成、构建通过和 UI 验收是不同状态，按证据推进。新交付发布及依赖关闭使用统一证据契约；存在依赖前置决策的后续阶段时，按[交付校验与阶段放行](references/delivery-and-phases.md)明确登记等待、带依据的新放行消息及实际产物回执，阶段待办未清不能判定完整闭环。恢复时先核对批次、版本、消息、回执与实际 Git/任务状态，再继续未完成动作；工具超时不证明成功或失败。

[持久消息工具](scripts/coordination.py) 提供原子落盘、消息 ID 去重、回执关联、旧修订识别、恢复汇总与接入意图防重；它不调用 Codex 工具、不执行 Git、不构建、不验证业务真伪，也不是后台调度服务。通信能力不可用时保留待通知记录，由主任务恢复后处理，不声称任务被唤醒或已执行。

源码原子提交遵守调用项目的实际授权及所属仓库规则。协作资料是否允许暂存、提交或改写历史也由该项目明确，不从技能本身推导权限；推送、PR、发布与真实业务外部写入须有对应授权。
