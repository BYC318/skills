# 源码交付与去重集成

多级结构先按 [分层集中集成](hierarchical-coordination.md#分层集中集成) 明确各仓库目标交付线的唯一负责人；下文 Git 流程由该负责人执行，上层核对子组汇总，不对已集成的同一目标线重复执行 Git 集成。“全部完成”按当前协调组冻结范围判断，跨组必要依赖仍须先关闭。

集成及最终验收前，按 [任务责任链](task-traceability.md#各层对什么负责) 核对原始验收项到本层/子组交付和实际证据的终版映射，登记到 `integration.json` 的 `requirement_coverage`；交付齐备不自动证明原始目标已覆盖。

## 启动分支、开发基线与 worktree

独立协作实际启动时，由调用窗口的协调者按每个真实源码 Git 仓库记录其当时检出的本地分支完整引用 `target_branch`（如 `refs/heads/feature/order`）和提交 `startup_sha`。前者是本轮最终集成目标，后者是不可变的开发起点；不是默认 `main`、远端默认分支，也不随后来切换窗口或检出其他分支而改变。相同 Git 根只登记一次，两端独立仓库分别登记；跨仓库公共来源也在自己的仓库登记。未绑定、无有效 HEAD 或 detached HEAD 时不能猜选目标，先解决该仓库的基线缺口，不隐式创建基线提交。

把启动快照写入 `batch.json.repositories`，至少包含稳定 `repo_id`、真实 Git 身份/路径、原源码 worktree、`target_branch`、`startup_sha`、upstream（存在时）、工作区及暂存区状态、唯一集成负责人；各任务工作区记录 actor、实际路径、工作分支和 `start_sha`。父子组沿用同一仓库的启动快照引用，不能到子组启动时重新采样另一个目标分支。

模块与仓库内共享任务都从记录的 `startup_sha` 显式新建独立工作分支及 worktree，并核对新 HEAD；本轮已创建的工作区在接续时核实后复用，不重复新建。不要省略起点，让创建工具从默认分支或创建时最新 HEAD 自行选基线。若聊天工具不支持该起点，先创建并核对正确 worktree，再让聊天使用它；无法绑定时保留阻塞，不在错误基线上编码。目标分支仍由原源码工作区承接最终回写；安全复用时可在该目录临时切换分支，不在第二个 worktree 强制重复检出同一目标分支。未提交改动不会随提交基线自动带入；保留原状，需要作为任务输入时明确其归属和接入安排，不擅自暂存、提交、stash 或清理。

**目标分支身份保持不变，分支上的提交可以持续推进。** `startup_sha` 仅记录最初切出 worktree 的位置，不冻结目标分支，也不作为最终合入时必须退回的提交。 开发期间该分支可以正常接收远端更新、人工提交或其他已授权任务的交付；目标前进不意味着本轮失效，也不要求所有模块重开。远端同步按项目流程和实际授权进行，不能把远端跟踪引用直接当作本地目标已更新。模块开发完成且满足本组集中集成条件后，交付分支先 rebase 到该目标分支当时的最新 HEAD，核验、复验后再快进合入同一分支。集成前及回写前均重新读取本地目标 HEAD，期间再次推进就重新 rebase、复验，保留新增提交；不把目标 reset 回 `startup_sha`，也不把目标分支 rebase 到模块分支上。目标删除、改名或历史被重写时先核对真实关系，不能自动换目标或覆盖现状。

本轮中断接续保留已记录目标和启动 SHA，核对其最新状态，不按当前检出分支重新绑定。确实开始新一轮开发时，再核对调用窗口指定源码工作区的当前分支及 HEAD，记录新快照和前轮关系；复用长期聊天不代表复用旧基线。

目录规划、真实聊天与工作/目标分支的对应关系按[工作区目录规则](worktree-layout.md)登记并展示；新任务按原源码仓库父目录下与仓库并列的 `worktree/<需求简称>/<平台>/<任务目录>/` 组织，已有路径和运行记录不为统一布局自动搬移。

## 集成工作区选择

候选集成 worktree 按需启用，优先安全复用原目标工作区；候选分支与候选 worktree 是两个选择，不要求一一对应。模块及共享任务开发时的独立 worktree 规则不变，也不为集成增加空聊天。

| 实际条件 | 选择 |
| --- | --- |
| 原目标工作区及暂存区干净、无在途 Git 操作，已确认本次可独占使用，允许必要的切分支与构建 | 优先复用原目标工作区 |
| 原工作区有须保留的未提交/暂存/未跟踪内容，或人工、其他任务仍需使用 | 不切换或清理原工作区；需要继续集成时另建候选 worktree，最终回写仍须等待原工作区安全可用 |
| 反复冲突处理或构建、证据采集需要独立源码目录，或项目明确要求独立环境 | 按实际收益建立候选 worktree；确认资源容量，不按模块数量机械创建 |
| 只因目标分支持续推进，或要求整批通过才回写 | 不据此强制新增 worktree；前者按最新目标重新对齐，后者可在原工作区使用候选分支 |

选择前核对真实 Git 根、symbolic HEAD、分支占用、工作区/索引、未完成操作、其他写入者和构建产物约束。不能安全复用且也不能建立合适隔离环境时保持阻塞，不用 stash、提交、reset、强制检出或直接改引用腾位置。唯一集成负责人统一安排写入，工具锁不能替代与人工及其他任务协调；不在整个模块开发期间长期占住目标工作区。

### 流程一：复用原目标工作区

1. 本组冻结范围的全部终版齐备后，取得本次集成时段的独占使用，重新核对记录的目标分支及最新 HEAD。
2. 按回写要求选择分支：允许逐项接纳时，在临时交付分支上 rebase、去重及验证，再切回目标分支逐项 `merge --ff-only`；要求整批通过后才回写时，在同一目录创建候选分支累计结果，整批复验通过后切回目标分支，一次快进回写。临时交付分支可以在已交接的执行工作区处理，也可以在本工作区串行处理；不得直接 rebase 目标分支。此流程均不要求新增候选 worktree。
3. 具体交付顺序、SHA 映射、目标再推进、验收及中断处理遵循下文[模块交付与协调去重](#模块交付与协调去重)。逐项回写也必须先等整批冻结输入齐备，不提前集成先完成的模块；后续步骤失败时保留目标已接纳的前缀，记录部分回写及剩余项，不 reset 撤回，也不报整批完成。全部纳入后仍复验最终组合。

### 流程二：独立候选 worktree

1. 原工作区暂不可用或确需隔离时，从记录目标分支的最新已核实 HEAD 建立本地候选分支及独立 worktree；不在第二个 worktree 重复检出目标分支，不复制原工作区的未提交内容。
2. 在候选工作区按下文共同步骤累计共享及模块交付、去重、rebase 和复验。回写前目标又推进时，保留新增提交，对齐最新目标后重新核验。
3. 最终在原目标工作区核对干净状态、真实分支和操作权限，再用 `merge --ff-only` 接纳已验证结果。原工作区仍不可安全操作时保留候选并记“待回写”，不能绕过原工作区直接更新目标引用；不自动清理来源分支或工作区。

在 `integration.json.repositories` 的 `integration_worktree` 填写实际用于累计集成结果的规范绝对路径，复用时可以与原源码 worktree 相同；`planned_actions` 记录选择理由、候选/目标分支、逐项或整批回写方式及独占安排。选择的工作区、分支与回写方式一并写入本次冻结输入；实际 rebase 和每次回写仍分别进入 `rebases`、`target_writebacks`。这些是 Agent 核实的执行计划，工具不自动判断可否独占或选择环境。恢复先核对记录与实际目录、当前分支和已回写前缀，再接续原计划；需改集成目录时保留旧冻结并按修订流程明确承接，不把换目录当作新一轮重复集成。

## 按共享类型选择交付方式

共享任务是否成立、类型及触发依据以 [技能正文](../SKILL.md#共享任务的职责与触发条件) 为准；未启用共享任务时，由模块交付自身提交，不生成空的共享清单或等待不存在的共享封版。

**仓库内共享代码**仅在模块开发时按清单 `cherry-pick -x` 消费共享任务提交，最终交付沿下文 rebase、去重及目标分支回写流程执行。源提交与消费 worktree 必须属于同一已核实的仓库身份；不能把两个平台各自的原生实现当作同一份公共源码。

**跨仓库公共依赖**先登记权威来源的真实仓库／路径、API 与兼容性、源码修订或发布版本、交付物哈希、消费者及项目既有接入机制。公共协议、SDK 或子模块等按实际项目使用的版本／锁定依赖、gitlink 或生成代码流程交付；平台适配和消费者仓库的接入改动由对应执行者分别提交和验证。共享来源在其维护仓库中提交、集成一次，各消费仓库保留自己的接入提交；不要求将公共来源提交 cherry-pick 到每个原生仓库，也不把消费者适配提交当成应跳过的公共副本。

消费者使用 `CONSUMED` 关联 READY、公共来源及版本、交付哈希、本仓库接入提交和验证证据；其 `page_commits` 列出本仓库应实际集成的提交。主任务在集成记录的 `external_dependencies` 中登记来源版本到各消费者接入提交／规范集成提交的映射，按真实仓库分别集成和复验；仓库内共享副本才使用 `shared_canonical`／`skipped_shared_copy`。已核实确为同仓库提交接入时再使用下文 Git 流程，不能按“共享任务”名称一概套用。

现有 `begin-action`／`finish-action` 只登记共享消费的 `cherry_pick` 动作；依赖版本更新、生成、最终 rebase 和快进回写分别保存意图与实际结果，恢复时核对真实状态，不虚构脚本支持新操作或自动验证依赖。

## 共享任务交付

共享任务可以在自己的源码分支按需求连续开发，不强制每个组件建立分支。每个原子提交只包含一个完整目的；组件的必要资源、工程引用、检查可以一起提交，不能混入无关需求。跨需求的公共基础独立提交，交付清单列明依赖，禁止循环依赖和无说明的 API 破坏性修改。旧能力可复用时优先复用，不为通信流程新建一套 UI 基础设施。

采用仓库内提交交付时，每份发布清单至少包含：`release_id`、需求 ID/修订、平台、稳定 `repo_id`、实际 Git 对象库/子模块身份、基线 SHA、按依赖排序的 `original_sha` 列表、各提交改动路径/用途/依赖、API 与使用示例、需求或设计依据及资源来源（UI 工作包含设计节点）、实际验证与剩余限制、消费者、清单 SHA256。不同源码仓库分开，不能跨仓库挑选同一个 ID；子模块内提交和宿主 gitlink 更新都明确记录。

主任务审核共享清单时逐条核对真实 Git 的完整 SHA、父提交、实际 diff、改动文件、用途及前置依赖，不只信提交标题。每条 `original_sha` 必须只含本次批准的公共改动；混有其他需求、模块私有实现或未批准文件时，由共享维护者先拆分/整理、验证并发布新版清单，不让消费者靠挑文件补丁或猜测提交范围替代准确交付。普通交付应为单父提交；merge 提交不作为常规 cherry-pick 输入，需要明确主线与重新整理并验证后的交付。必要基础若没有交付或无法独立挑选，先补齐；不带入无关历史填补依赖。

## 模块执行按需接入

本节适用于同仓库提交接入；跨仓库公共依赖按前述依赖交付方式处理。

接入前先按 [恢复工具](recovery-tool.md) 扫描未完成请求和历史执行结果，再用 `begin-action` 登记每条源提交在目标 worktree 的执行意图。已有记录或结果未知时不直接重做，先核对真实 Git；实际成功且核验后用 `finish-action` 保存本地 SHA 与依据，再发布 CONSUMED。每条意图与完成回执是本机协作资料，不放进源码提交。

1. 核对角色、源码仓库、分支、工作区和本端提交审查规则。页面独立单元先提交，不把公共同步与页面代码混在一个提交；未完成改动不能擅自 stash/丢弃以便接入。
2. 读取当前有效 READY 所引用的 `release_id`、需求修订、真实共享来源仓库、不可变清单及 SHA256，核对本模块确为消费者。明确列出这次需要接入的完整 `original_sha`，每项写明用途、实际改动路径、依赖及其已满足/本次接入状态；逐项查看真实提交 diff，确认只包含已批准的共享代码。清单不存在、哈希不符、来源不明或依赖缺失就保持阻塞，不从共享分支最新 HEAD、标题、时间区间或聊天中的简称猜选。再核对目标 worktree 未处于 cherry-pick/rebase 等操作，并查历史映射，已接入项不重复执行。
3. 对已批准清单按依赖顺序逐个 `git cherry-pick -x`；不使用提交范围表达式带入未批准历史，不调用 `git merge` 合入整个共享分支，也不直接从其他 worktree 复制活动文件。命令只作用于当前本端 worktree，不含 push。
4. 每个成功动作记录 `release_id` / 清单哈希、当前 READY/需求修订、消费者 worktree，以及 `(repo_id, original_sha) → applied_sha`、实际文件差异和验证。发生冲突时另记冲突文件、实际解决差异及维护者确认，不能声称消费副本必然与源补丁完全一致；`CONSUMED` 与最终 RESULT 的 `consumed_shared` 逐项引用这些记录，使每次通知、接入及最终去重都能追溯准确来源。默认 cherry-pick 新建提交，A/B 的公共副本 ID 通常不同；这不是唯一维护者规则被破坏。冲突解决后核对来源标记，`-x` 不能当成自动去重或完整依赖证明。
5. 失败时写 BLOCKED，保留已成功项和当前操作状态，不自动 `--skip`、`--abort` 或用 ours/theirs 覆盖。接收重复通知时核对历史和来源回执，不盲目再次挑选。没有文本冲突也要检查构建、API 和页面行为。
6. 公共实现仍由共享任务维护。页面可配置公开参数和回调，公共缺口重新提需求；发现模块执行任务私改公共文件或在页面目录复制同类实现，主任务退回处理。工程文件和资源索引也必须事先确定归属，不能只保护组件源码。

命令格式（`真实完整提交ID` 须来自已审查清单）：

```bash
git cherry-pick -x 真实完整提交ID
```

## 模块交付与协调去重

以下公共副本去重针对同仓库提交接入；跨仓库公共依赖遵循上节的来源版本与消费者提交映射，集中等待和职责边界仍适用。

本节“全部任务完成”指本批已登记参与者完成本批冻结的需求修订，不是全部长期模块未来都没有需求。后续需求复用原任务，批次切换、基线核对与交付撤回按 [长期接续流程](lifecycle.md) 执行；冻结后不覆盖原交付清单。

模块执行的 RESULT 附实际分支、起点及冻结 HEAD，并分开提供 `consumed_shared` 和 `page_commits`（沿用字段名，表示模块独有提交，不要求存在页面）。前者是原始公共 SHA、本地副本 SHA、需求修订与验证；后者是该页面独有的有序原子提交及实际改动路径/依赖/证据。混合提交不能仅靠标记为“页面”绕过范围检查，应先整理出单一目的交付。

默认集中集成，不边开发边汇总：本次约定范围内所有参与执行任务完成、实际存在的共享交付封版、提交清单与所需证据交齐、未完成 Git 操作和依赖阻塞处理完，主任务才冻结集成输入并开始按 rebase 流程集成。先完成的任务只交终版资料后等待。原子提交仍在任务内及时完成，不能把“等统一集成”理解为积攒一个大提交。模块与共享交付经 rebase 保留原子提交边界，不压成一个提交。

主任务在 `integration.json` 记录参与任务、各终版交付的版本/哈希、是否全部齐备、未解决项和实际集成开始时间。 齐备后按[执行资料防护](execution-guards.md)用 `freeze-integration` 一并登记不可变输入快照与 `scope_freeze`，开始、恢复集成及最终核对时运行 `check-integration`，不能只保存清单却保留模板“未冻结”状态。缺一个参与任务的终版交付就保持等待或阻塞；用户明确调整范围时更新原授权范围及排除依据，不擅自划小批次提前集成。后续集成发现问题，定向安排受影响任务修正，按修订清单继续本次集中集成，而不是让所有任务重新互相沟通。

主任务以 [集成记录模板](../assets/集成记录模板.json) 为起点，按前述选择复用原目标工作区或使用独立候选 worktree，在明确授权的源码工作区中执行以下共同步骤；协作资料仓库的写入及 Git 权限按项目配置和实际用户授权核对，不从源码授权推导：

本节的主任务指跨聊天协调者，负责 Git 集成及证据核对，不接管已分配给其他执行者的冲突修复或适配工作。发现冲突时保留现场，登记受影响文件及当前 Git 操作，暂停该 worktree 的其他写入，再由页面或共享代码所属执行者修复，其中包含该模块内部主 Agent；涉及双方契约时先统一契约。需要更换执行者时，核对在途动作、确认原执行者停止相关写入并记录交接。协调者核对修复及验证结果后再继续集成，不与修复者并发操作同一 Git 状态。单 Agent 或模块内部主 Agent 对自身范围的修复不受“协调者不接管”限制。

下文“累积分支”指整批回写时的候选分支，或逐项回写时的目标分支，与是否另建 worktree 无关。分支切换与关键步骤前后按[执行资料防护](execution-guards.md#候选分支身份与累积结果)使用 `switch-candidate`／`check-candidate`，传入实际候选或目标本地分支、完整 HEAD 及已纳入的规范祖先；detached、分支不符或漏累积时不继续。临时交付分支完成 rebase 后也核对真实附着分支及预期 HEAD，不把其误认为目标分支。实际rebase/验证脚本用同页 `run-scripts` 先预检所有绝对路径，再按退出码串行执行，前一步失败时不验证旧候选。外部脚本执行意图与回执关联本节的 `rebases`／`target_writebacks`，中断先对账，不盲目重跑。

1. 确认终版输入齐备，冻结各来源分支/HEAD、基线、提交清单、公共消费映射及交付哈希。重新读取记录的 `target_branch` 最新 HEAD，按登记的工作区与回写方式，以它为基点准备累积分支；使用候选分支时只暂存验证结果，最终仍须回到该目标分支。记录目标这段时间的推进，不因它已多出提交而改回启动 SHA。
2. 先处理共享交付：从冻结的共享 HEAD 创建本次可变交付分支，将其交付范围 rebase 到当前累积分支 HEAD，验证后再快进累积分支；直接更新目标时同时执行下文回写核验并保存本次回执。已有公共项先查真实祖先关系、来源映射和实际实现，只保留一份规范结果。无共享任务时跳过，不创建空交付。跨仓库公共来源与各消费仓库的适配仍分别在所属仓库集成。
3. 再按依赖顺序处理每个模块：从冻结模块 HEAD 创建交付分支，用已核实旧基点和当前累积分支 HEAD 界定 rebase 范围（按需使用 `rebase --onto` / 交互式 rebase）。只重放本批已批准的模块独有提交；把 `consumed_shared` 中已被规范公共结果覆盖的副本逐项映射后排除，不能把整条含副本历史直接合入。不能用协调者逐条 cherry-pick 模块提交代替最终 rebase 集成。
4. 去重依据是稳定仓库身份、公共原始完整 SHA、消费副本与规范结果的映射，并核对实际 diff、API 与树状态；`git patch-id --stable`、`-x` 标记或 Git 自动跳过补丁都只是辅助。公共副本包含冲突修复、消费者适配或额外改动时，先交所属执行者分离/核验，不能整条丢弃。模块独有提交变空或被跳过也要逐项查明，不能因为 rebase 成功就认定无代码丢失。
5. 每个交付分支 rebase 完成后，核对旧/新有序提交（可用 `git range-diff` 辅助）、公共唯一性与模块行为，记录来源 SHA → rebase 后 SHA，验证后快进累积分支；直接更新目标时，每次均执行下文回写核验并保存回执。保留原子目的和提交边界，不 squash、夹带无关历史或改写冻结交付清单；原始来源分支保留供追溯。这里允许改写本轮明确的交付分支，不授权改写目标既有历史或其他人的分支；若要 rebase 原执行分支，先确认原执行者停止相关 Git 写入并完成交接。
6. 保存每次 rebase 的意图与实际结果：仓库、工作区、原基点/HEAD、onto SHA、批准清单、排除项及理由、新 HEAD/提交映射、冲突和验证；状态区分 `planned`、`in_progress`、`completed`、`blocked`、`unknown`。中断先查真实分支、rebase 状态、reflog 和现存提交，补齐回执，不直接重新运行，也不让两个聊天同时操作该 worktree。现有 `begin-action` / `finish-action` 仍只识别 `cherry_pick`；rebase 与回写由 Agent 在 `integration.json.rebases` / `target_writebacks` 留证并实际对账，不能伪称工具已自动执行、去重或恢复这些操作。
7. 回写前再次读取同一 `target_branch`。使用候选分支且目标继续前进时，以上次对齐的目标 HEAD 为已核实旧基点，仅将本轮候选集成增量 rebase 到新的目标 HEAD；直接逐项回写时保留已纳入目标的前缀，只将剩余交付 rebase 到最新目标，不重写已合入目标的提交。更新来源到最终 SHA 的映射、公共副本核验及受影响证据，再验证，不能覆盖目标新增提交；每次拟回写结果均须包含已知目标最新 HEAD。集成负责人安排执行者对最终累计结果按项目配置重新构建、测试及复验受影响范围；UI 证据另建真实轮次，不能改名冒充集成构建。持续更新时协调一个短暂回写窗口，不要求开发期间锁住目标分支。
8. 每次实际回写前核对原目标工作区、暂存区、在途 Git 操作和分支占用，确认独占且实际附着于记录的目标分支；同目录候选模式先安全切回目标分支。将本次已验证的交付或整批候选结果以 `git merge --ff-only` 快进到该目标分支，不把目标分支合入自身；这是 rebase 后的快进更新，不创建 merge commit。目标在检查后又前进导致不能快进时，重新对齐本次待接纳交付或候选增量并复验；不强推、不 reset、不直接改引用绕过已检出的工作区。未提交或暂存改动影响安全回写时保留现场并列明阻塞，不擅自 stash/提交/覆盖；候选已通过而未回写只记“待回写”；逐项回写尚未覆盖整批或最终组合复验未通过时记“部分回写／待复验”，均不记最终集成完成。
9. 记录目标回写前后 SHA、实际命令结果及验证来源，确认本次交付提交已纳入该目标分支，逐项回写另核对整批冻结清单无遗漏；若目标在回写后又正常前进，保留后续提交并以祖先关系确认本轮交付仍在，不要求永久停在某个最终 SHA。回写成功但回执未保存时先查真实 Git 补记录，禁止重复集成。验收与目标回写分别记录，任一未完成都不能宣布本轮全部完成；不自动删除源分支/worktree，不推导推送或其他发布权限。

## 这套选择的代价

模块开发时的共享 cherry-pick 与最终 rebase 都不能保证无冲突；负责人仍须核对交付范围、提交映射和公共副本去重，目录归属也不能防止公共 API、主题、依赖或工程配置带来的语义问题。已知依赖必须登记；若清单无法准确整理或改动高度耦合，就缩小并发、顺序完成，而不是不断增加消息协议或强行自动合并。

Git 语义依据：[cherry-pick](https://git-scm.com/docs/git-cherry-pick)、[rebase](https://git-scm.com/docs/git-rebase)、[快进更新](https://git-scm.com/docs/git-merge#Documentation/git-merge.txt---ff-only)、[patch-id](https://git-scm.com/docs/git-patch-id)、[worktree](https://git-scm.com/docs/git-worktree)。消息工具不执行这些 Git 动作，实际命令遵守平台规则与批次授权。
