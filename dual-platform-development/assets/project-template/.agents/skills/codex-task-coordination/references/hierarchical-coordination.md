# 多级独立聊天协调

## 按工作量选择层级

规划咨询先读取本节及 [只读规划与实际启动](../SKILL.md#只读规划与实际启动)；方案中的数量指独立聊天任务，不能替换成真人编制。

可以采用“双端协调聊天 → 端内协调聊天 → 模块执行任务及端内共享任务”，必要时由双端协调聊天协调跨仓库公共依赖任务。只有当本端存在多个可独立推进的模块、端内依赖或明显的协调负担时，才增加端内协调聊天；两端规模不必相同。小任务可由双端协调聊天直接协调模块，单个执行聊天也可直接完成自身工作，不要求建立全部层级和角色。共享角色仍按 [两类共享任务条件](../SKILL.md#共享任务的职责与触发条件) 设置。两端各只有一个模块执行任务时，由双端协调聊天直接协调；两端源码独立且不存在共同公共来源时，不启动端内共享任务，本端公共代码调整由对应模块执行承担。若两端实际共同修改同仓库同一份代码，可由共同上级协调唯一的仓库内共享维护者；真正跨仓库公共依赖仍按其独立触发条件判断。已有归属先恢复并按需交接，不能由两端数量推导出固定共享角色。

先按完整业务归组，再决定执行任务数量。高内聚指同一任务内的需求共享业务目标、状态或数据、修改原因和验收结果；不能只因都是弹窗、列表或设置项，就把互不相关的业务塞进一个任务。

- 同一平台内，同一业务的入口、页面、弹窗、角色状态、异常处理及相关验证归同一个长期模块任务。不按页面数量、浅色/深色、LTR/RTL、UI/逻辑/测试阶段拆成不同业务执行聊天；独立质量审查仍按项目要求执行。后续同类需求优先追加给原业务任务，已有归属变化须交接。
- 先列业务分组及覆盖需求，再核对源码文件、状态所有权、公共依赖和验收。完整业务任务并行启动；有依赖的任务先推进本地可做部分，接口或实现未交付不作为整任务的启动门槛。真实接入和依赖验证在前置条件满足后进行。同一组过大时，只按真实独立子业务拆分并保留明确归属，不把同一状态的不同表现分散开发。
- 对公共文件重叠，先明确唯一维护者及调用接口；满足共享任务条件时独立维护真实公共实现。不让各模块重复开发同类能力，也不因存在公共依赖就把整端业务全部串行。只有无法合理分开且必须一起修改、验收的工作才合并。
- 方案同时说明集中执行会让哪些独立业务排队，以及并行增加哪些沟通、集成和返工成本，优先缩短整体交付周期。最终每端一个任务必须有已核实的范围、耦合或资源依据；每端多个也必须有完整业务和文件边界依据，两端数量不必相同。

默认让本批已授权、职责和源码边界明确的全部执行任务并行启动。缺依赖时记录 TODO 并持续推进本任务可做部分，只让依赖对应的接入和验证等待；构建、设备和同工作区 Git 操作仍分别排队。工具并发硬限制或实际资源不足时说明真实限制及排队任务，尽量用满可用容量，不假报全部正在运行。业务任务总数、实际运行数与待调度数、构建/截图容量分别展示。代表性试跑用于发现问题和校准耗时，不要求其他业务等待试跑全部完成；只有已核实会影响其正确性的前置问题才限制对应工作。

规划至少给出每个任务的业务目标、覆盖需求/状态、平台及可写范围、公共能力唯一维护者、前置依赖、启动条件和验收结果。先作有依据的候选分组，未核实项明确列出并补查；正式分派前核实边界。协调与共享角色单独计数，只有端内确有调度收益时才增加协调层。例外选择集中执行时，按 [启用价值评估](../SKILL.md#启用价值评估) 说明具体原因，不为凑数量拆碎需求。

这些任务均为可长期接续的独立聊天。模块和共享聊天内部可直接开发或派生子 Agent；总协调聊天内部只处理协调、只读核对及已授权集成。内部子 Agent 不登记成下级独立聊天。维护配置不创建聊天；增加下级聊天和通信链路仍须在可核实的用户授权范围内，不能由上级消息自行扩大权限。

## 缺依赖时持续推进

依赖只阻塞具体接入点，不默认阻塞整个业务任务。执行者先列出当前能实现、能独立验证及必须后接的部分，持续推进前两类；有可做工作时不得只写 BLOCKED 就停工等待。

- 在已有任务记录和接入位置记录可追踪的 TODO：依赖/需求 ID、提供方、需要的接口或实现、已确认契约与待确认项、接入位置、受影响验收及下一动作。不能只留“以后对接”的无归属注释；协作模式中按现有协议提交依赖请求，源码 TODO 引用同一记录，不另建一套消息系统。
- 按已确认契约推进调用侧和本地业务；契约未定时隔离待接点并标明假设，不擅自把猜测定成公共 API。确需临时适配或测试替身时保持本地、可替换并明确未接通，不复制公共实现、不修改其他任务负责的文件，不以假成功掩盖缺口。
- 依赖就绪后，由原业务任务按 READY/接入协议补齐真实实现、移除失效占位与 TODO，并重跑受影响的构建、交互和运行证据。协调者跟踪未关闭项并通知负责方，不代写源码。
- 只有本任务当前所有可独立推进的工作已做完时，才保存进度并报告剩余受阻项，按恢复协议等待。局部实现完成、测试替身通过不等于真实接入完成；本次交付范围内必需的 TODO 未关闭，不得声明整任务完成或通过最终验收，集中集成及阶段放行要求保持。

## 每轮回复的任务结构图

涉及本协作任务的规划、分工、方案调整、进度汇总或阶段/整体交付时，每轮最终回复必须展示当前完整任务层级图；结构未变也保留，不要求用户再次提醒，不只写“结构同上”或只展示本轮改动。规则维护或无关问答不据此虚构业务任务。

- 优先使用内嵌 Mermaid 层级图，展示双端协调、实际采用的端内协调、全部模块任务及有依据的候选/已设共享任务。每个聊天节点代表一个独立 Codex 聊天，连线表示直属协调关系；不混入聊天内部子 Agent。图太大时可拆为总览与各端完整子图，保留上下级连接和全部节点，不用“等”“其余同上”省略任务。
- 规划时就按 [窗口命名](#独立聊天窗口命名) 给出每个节点的完整拟用标题，不能只写“iOS 总协调”“登录注册”或内部逻辑 ID，再等创建后补名称。可以换行排版，但需求简称、平台、角色、业务名称不能缺失；协调节点不强加业务模块。
- 在图注或节点状态中区分候选未创建、已创建及当前执行/完成情况。创建状态与进度只使用已核实记录；没有核实时明确待核对。当前聊天显示其拟任角色；实际标题不同则注明拟用名称，不能以展示名称冒充已经改名。已有节点按真实聊天 ID 绑定，调整方案不代表已经创建、改名或归档。
- 调整后重画当前有效完整结构，简述本轮新增、合并、拆分、撤销或更名；同时更新图内标题、分工说明和数量，不能让新旧方案混用。图后分别列协调、模块及共享任务数量，候选与已创建分开，编码并发与构建/截图容量分开，不把总数当同时运行数。

## 独立聊天窗口命名

规划图、分工清单与实际侧边栏标题统一按“需求简称＋平台＋任务角色＋具体模块”排列，显示为 `需求简称｜平台 任务角色｜具体模块`。同一需求各层使用同一需求简称，取自共同原始目标；平台和角色按实际职责填写，模块执行必须写明登录、首页、设置等具体范围，不能仅用 A/B 或内部逻辑 ID 代替。协调聊天不填模块；共享任务需要区分公共来源时再补范围。

| 实际角色 | 标题示例 |
| --- | --- |
| 双端协调 | `应用改版｜双端总协调` |
| iOS 端内协调 | `应用改版｜iOS 总协调` |
| iOS 模块执行：登录 | `应用改版｜iOS 子任务｜登录` |
| iOS 模块执行：首页 | `应用改版｜iOS 子任务｜首页` |
| iOS 模块执行：设置 | `应用改版｜iOS 子任务｜设置` |
| iOS 仓库内共享 | `应用改版｜iOS 共享任务`，需区分时用 `应用改版｜iOS 共享任务｜公共存储` |
| Android 端内协调 | `应用改版｜Android 总协调` |
| Android 模块执行：登录 | `应用改版｜Android 子任务｜登录` |
| Android 仓库内共享 | `应用改版｜Android 共享任务` |
| 两端实际共同消费的公共来源维护 | `应用改版｜双端共享任务｜公共 SDK` |

以上是命名示例，按真实参与平台、模块和共享来源替换，不据此创建额外聊天或把契约讨论变成共享开发任务。“总协调”“子任务”是面向用户的标题称呼，分别对应协议中的“双端协调／端内协调”“模块执行”；`main`、`worker`、`shared` 等协议角色保持不变。

当前协调窗口也执行同一规则：本轮只协调 iOS 的模块时命名为“需求简称｜iOS 总协调”，Android 同理；仍负责两端时命名为“需求简称｜双端总协调”，即使只有其中一端拆多个模块也不改成该端总协调。省略端内协调层时，当前窗口按实际覆盖范围命名；一个聊天兼任上下层角色仍只有一个标题，目录中保留其全部职责与真实身份，不为了标题补建层级。

完整拟用标题在规划阶段即确定并展示；需求简称或分工调整时先同步方案和结构图，不自动操作真实聊天。实际启动协作时，创建独立聊天用 `create_thread.title` 明确传入当前方案中的标题；当前协调窗口及复用聊天由所属协调者核实身份与本轮范围后，用 `set_thread_title` 更新。按工具实际返回或读取到的名称登记长期目录中的 `tasks.<逻辑ID>.title`，需求简称登记在 `requirement_short_name`；标题更新失败时保留待更新状态，不假报已命名，也不另建替代聊天。

标题用于展示，真实 `thread_id` 才是聊天身份；改名不改变逻辑 ID、批次、源码归属、消息路由或 worktree。接续仍先按真实 ID 恢复；转入新需求时更新展示标题并保留旧需求引用，不因改名丢弃历史。仅维护或同步技能不改名历史演练聊天，不创建聊天或继承旧通信授权。

窗口标题与目录、源码工作区及分支的对应按[工作区目录规则](worktree-layout.md)登记；资料目录不等于 Git worktree，改名不自动移动工作区，也不要求每个协调聊天额外创建源码副本。

## 各层职责与协调组

双端总协调和端内总协调是专职协调角色，只负责拆分、分派、依赖沟通、只读审查、证据核对、协作资料及已授权的 Git 集成，不承担业务代码、公共代码、工程引用或源码冲突修复。不能通过给自己预留模块、临时改称执行者或在协调聊天内派生编码子 Agent 绕过分工；需要改源码时交给模块或按需设置的共享任务。单 Agent 独立开发及模块、共享任务内部主 Agent 仍可在自身授权范围直接实现、修复、构建和验证，也可按需派生子 Agent。总协调不能兼任模块或共享代码维护者；已授权集成出现需要改源码的冲突时，交所属执行者处理后继续核验。

| 角色 | 负责范围 | 对外交付 |
| --- | --- | --- |
| 双端协调 | 统一需求与共同契约、跨端依赖、各端交付范围及最终联合验收；协调必要的跨仓库公共来源 | 各仓库已核实的集成结果、跨端一致性及整体未完成项 |
| 端内协调 | 在本端范围拆分模块、路由端内公共需求、协调资源与本仓库集成验收；向上汇总跨端影响 | 本端冻结的交付清单、规范集成 SHA、验证及依赖状态 |
| 模块执行 | 在分配的 worktree 实现和验证模块，按清单接入公共代码，提出所需依赖 | 模块独有提交、公共消费映射和证据 |
| 共享任务 | 唯一维护已登记公共代码或公共依赖来源；归入覆盖其实际消费者的协调组 | 公共原始提交或来源版本、兼容性、消费者与验证 |

各层分派和交付须遵循 [任务目标与分派责任链](task-traceability.md)：原始目标及有效验收贯穿各层，中层负责覆盖检查和核验汇总，不能只转发标题或“子任务完成”。

一名协调者和它直接调度的独立聊天构成一个“协调组”。协议中的“主任务”／`main` 指当前协调组的双端协调或端内协调，不天然指最外层。每组使用独立的长期目录、批次根路径和唯一批次 ID，每批仍只有一个 `main`，只登记直接参与者。端内协调聊天在父组登记为 `worker`，在自己的子组登记为 `main`；沿用同一个真实聊天 ID 和稳定逻辑 ID。例如父组的 `ios` 为 worker，子组的 `main` 字段填 `ios`、`actors.ios.role` 填 main，同一端内协调身份不重复创建聊天。长期目录的 `main_task_id` 与本组批次的 `main` 保持一致。没有子组时保持原有单层结构。

所有协调角色只在自己登记的范围调度，不接管已分配源码。子组可接受上层目标和契约，但父组不再重复向同一源码分派写入任务；归属变化须核对在途动作并交接。上下层共用设备、工具会话或 Git 工作区时仍须统一排队，层级和目录不提供物理隔离。

## 目录与批次关联

[长期目录模板](../assets/长期任务目录模板.json) 和 [批次模板](../assets/批次模板.json) 的 `coordination_group` 是 Agent 维护的可选元数据，使用以下约定：

- `group_id`：项目内稳定的 ASCII 协调组 ID，单层旧记录缺失时按原组恢复，不自动重写历史。
- `parent`：顶层为 null；子组登记父组 `group_id`、`registry_path`、当前协调聊天在父组的 `actor_id`。批次快照另登记父批 `batch_id`、`coordination_root`、上层分派的 `entity_id`、`revision` 和 `message_id`。
- `children`：仅记录实际存在的直接子组，每项包括 `group_id`、`registry_path`、`coordinator_actor_id`、真实 `thread_id`；当批快照另记 `batch_id`、`coordination_root`、本批要求的 `delivery_scope`。父子两侧核对协调聊天身份及绑定一致，不把空模板当成已创建。
- `collaboration_assessment`：批次中的组织方式与理由（`decision`、`reason`）、实际任务计划（`task_plan`，逐项记平台/范围、角色及拆分依据）和并发/资源约束（`resource_limits`）；协调、执行与共享角色分别计数，元数据由 Agent 维护，脚本不自动评估。
- `repository_owners`：登记真实仓库身份、启动时当前目标分支/交付线、启动快照引用、负责协调组/聊天和实际集成 worktree。父子组沿用同一目标，HEAD 可正常推进；不在下层另采默认分支。长期目录保存当前归属，批次保存本轮快照，开始集成前双方核对。
- `cross_group_links`：由本组主任务维护的跨组转述索引，保存源与目标的组、批次根、消息 ID、实体/修订、转述用途、状态及下一动作。源事件、目标事件和实际回执为依据，索引不代替不可变消息。

各组长期目录的 `batches` 只索引本组批次；通过 `children` 引用子组目录，不把所有层级批次塞进同一份目录再用同一个 actor 扫描。父组控制资料由父组主任务写，子组控制资料由子组主任务写；子组通过消息请求更新父侧状态，不共同改写父目录。项目原有统一 UI 台账及工具的唯一写入约定保留，各层交付证据索引，由项目指定维护者统一收录，不另建重复总台账。

现有脚本继续使用 schema 1 和原消息 envelope；上述层级元数据由 Agent 核对，脚本不递归发现子组或执行转述。显式登记阶段放行时，工具仅核对本组或已绑定直接父组的消息依据及约定产物，具体见[交付校验与阶段放行](delivery-and-phases.md)。配置路径、授权来源和快照须传至每个实际参与组；不能从父组身份推导新增仓库权限。

## 消息逐层路由与闭环

端内模块和端内共享任务经本端协调者路由；只影响本端实现的需求在本端处理。涉及共同契约、另一端、跨仓库公共来源或上层承诺范围时，经端内协调聊天上报双端协调聊天，再由其下发受影响的端。跨组依赖经最近的共同上级协调；共享来源只设一个维护归属，不能在多层重复安排维护者。省略某层时由实际直接上级履行相应职责。

每条消息仍必须经过所在批次的 main。转述者在目标批次以自己的本组身份发布新事件，使用新消息 ID；原事件不移动、不改写、不伪装发送方，不把跨批事件 ID 放入本批 `refs`。转述消息的 `payload.upstream_refs` 或 `payload.downstream_refs` 登记来源 `group_id`、`batch_id`、绝对 `coordination_root`、`message_id`、`entity_id`、`revision` 和交付哈希（存在时），供实际读取核对；`refs` 只引用目标批次已有消息。

例如模块 A 需要跨端依赖：A 在端内批次发 REQUEST → 端内协调聊天在父批次发 REQUEST → 双端协调聊天分派公共来源并审核交付 → 向端内协调聊天发 READY → 端内协调聊天在端内批次发 READY → 模块接入并发 CONSUMED → 端内协调聊天核验后在端内关闭，并在父批次发本端 CONSUMED/RESULT → 双端协调聊天核验后关闭父侧依赖。涉及多个模块时逐消费者保留状态，一个模块完成不能替其他模块关闭。

端内协调聊天在父批次是 worker，向上汇总使用 REQUEST、RESULT、BLOCKED 或 CONSUMED；不能直接冒用 shared 发送 RELEASE。子组共享任务先向本组 main 发 RELEASE，经审核后由端内协调聊天在父组提供带真实来源的汇总。ACK 只证明某一跳收到，子组完成或上层 READY 均不证明最终模块已经接入。父组的 RESOLVED 必须引用父组相应消费者、同实体/修订的 CONSUMED/RESULT，且其 `payload.verification` 含实际通过状态与证据；子组回执通过 payload 关联，不能直接充当父批次 `refs` 或关闭证据。取消、延后及失效同样逐层记录和通知。

转述不是跨组原子事务。转述者先在自己担任 main 的协调组目录 `cross_group_links` 保存来源、目标、确定的目标消息 ID 和“待发布/待通知”意图（作为父组 worker 时不改写父组控制资料），发布后补实际事件、通知与确认状态；同一转述重试沿用原目标 ID 和内容。补发前先核对两侧有效修订；旧意图已被新版取代时，保留其历史和取代关系，核实旧目标是否已发布或执行，再为当前有效修订登记新转述，不机械补发旧 READY、覆盖旧消息或继续已失效动作。恢复时核对两边磁盘和真实聊天后补缺的一跳，不因已 ACK 源消息丢掉尚未转述的请求，也不在结果未知时重新生成转述。无须为每个普通提交或进度逐层汇报；只转述必要依赖、范围/契约变化、阻塞和终版交付。上层未运行时保存待转述及阻塞，继续无关工作，不虚构后台唤醒或擅自绕过分工。

## 需求决策与修订

跨层前置条件满足、需要下层继续后续阶段时，按[阶段放行](delivery-and-phases.md#将等待与放行明确记成消息)发布携带当前上层依据的新消息，显式承接原等待；不能只在父组关闭后通知仍写着“等待父组”的旧消息。协调者核对下层实际阶段回执及产物后再汇总，ACK齐全和旧交付已关闭都不证明后续阶段完成。

双端共同契约由双端协调聊天统一决策，端内实现由端内协调聊天在已授范围决定。共享契约变更先交有权的共同上级，不能由一个端局部批准后声称两端已接受。用户直接在任一聊天追加需求时，保存原始授权并向有权决策层逐级同步，原授权内不受影响的工作继续。

同一需求实体跨层传播时保持 ID 和权威修订；端内协调聊天在子批次以 main 发布对应 ASSIGN/READY 后再执行，保存上层决策来源。拆成独立子需求时使用新的稳定实体 ID，登记父实体/修订及依赖；子需求可独立修订，但不能覆盖上层共同契约。上层增版后逐项核对子需求和消费者，记录沿用、调整或取消；新修订不会自动停止已运行任务或撤销代码，须通知并核实实际状态。未完成映射或确认的变化部分保持待核对；重新分派受影响源码前须确认旧执行者停止相关写入并交接。各组工具只校验本批修订，跨组一致性由协调者按映射核实。

## 分层集中集成

各组只等待本批冻结的直接参与者及真实依赖。省略端内协调、两端同属一个冻结协调组时，一端先完成仍须等待本组交付条件齐备，不能临时拆批或缩小范围提前集成。子组完成本端全部约定模块、实际共享封版和必要验证后，可由已登记的集成负责人集中集成本仓库，无需等待无依赖的另一端；父组等待的是约定的本端汇总交付。影响公共契约或跨端依赖未关闭时，受影响子组继续等待，不擅自拆小批次或缩小范围绕过冻结条件。

同一真实仓库、同一目标交付线在一个交付周期只有一个集成负责人，父子组均记录同一归属及实际集成工作区；优先安全复用原目标工作区，需要隔离时才另建候选 worktree。通常由端内协调聊天负责本端源码集成，双端协调聊天审核两端规范结果并做联合验收；没有端内协调聊天时由实际承担该仓库集成的协调者负责。按 [分支基线与源码交付规则](code-delivery.md) 区分开发与集成基线：模块及仓库内共享 worktree 从固定启动 SHA 切出，新建候选分支时以已核实的目标最新 HEAD 为基点；交付集中 rebase 到该目标最新 HEAD 并快进回写；同仓库公共改动只保留一份规范结果，跨仓库公共来源和各消费者接入提交分别在所属仓库处理。

子组交付不可变汇总：本批范围与修订、后代终版交付及全部未关闭依赖/未知动作、子批次根和清单哈希、真实仓库/基线、按顺序的来源与 rebase 后规范 SHA、公共副本映射、目标分支回写前后 SHA 和实际回写状态、最终 HEAD、实际构建/测试/证据和未解决项。父组在 `integration.json` 的 `child_deliveries` 中登记上述子组交付及接收结论，子组在 `parent_delivery` 登记向上交付的版本/哈希和父侧回执引用；单层时分别为空数组/null。不能仅凭“本端完成”声明通过，须核对当前冻结范围、全部相关后代和跨组依赖、未知动作以及证据实际来源。已由子组完成目标回写的仓库，上层核对实际分支与祖先关系，不再重复 rebase、cherry-pick 或 merge 同一目标线；仅有候选集成结果而未回写时，子组仍须明确待办。

若确有另外的发布分支接入，先登记该目标交付线、授权、冻结输入和唯一负责人，沿用 [源码交付与去重规则](code-delivery.md) 记录来源、动作与实际 Git，不把它混成对原目标线的第二次集成。上层发现缺陷时交所属端/模块修正，保留旧清单并交付新版本；改变最终 HEAD 或公共版本会使受影响汇总和证据失效，逐层重新核对。各组脚本锁和接入防重只作用于本批，不能声称已有跨组互斥或全局去重。上层等待终版不阻止开发期必要公共依赖 READY 的下发，避免父层等终版、子层等依赖的循环。

## 分层接续与结构调整

恢复先读取本组、父组绑定和直接子组索引，核对实际聊天及当前用户纠正；分别运行本组 `recover --registry` 和所有影响本轮交付的子组恢复，子组使用它自己的 main 逻辑 ID。脚本不递归处理 `children`；同一聊天兼上下层协调时，要分别扫描父组中自己的 actor 和本组 main 两种范围，不能把一次扫描当成整棵树已恢复。更深层同样逐层核对，父组取得带批次、快照、核对时间和缺口的恢复摘要；需要时只读查证原事件，不能代替所属层发布决策。

恢复顺序是：有效契约及父子批次绑定 → 各组待确认事件/未知动作 → 尚未完成的转述及需求映射 → 真实 Git/集成归属 → 子组冻结交付和证据 → 未关闭消费者及下一动作。子组无法读取、绑定不一致或结果未知时保留该分支待核对；无关分支可继续，但不能宣布全局对账完成。父侧依赖不能因子组完成标记关闭，也不能因父组暂未运行就忽略子组在途写入。

追加需求复用原协调及模块聊天，各组批次可以独立推进；登记本轮父批对应哪些子批和哪个范围/修订，不以“子组最新批次”替换父组已冻结的交付。冻结后变化按 [长期接续规则](lifecycle.md) 保留旧快照、更新受影响映射并重新验收。

新增、合并或撤掉协调层只在确有工作量需要且具有相应用户授权时进行。先核对原聊天、未关闭消息、转述意图、写入和 Git 动作，完成职责/集成归属交接，再调整目录链接并通知受影响者；不自动删除旧批次、迁移不可变事件、归档聊天或复制共享维护者。没有层级字段的旧项目继续单层协议，在接续记录补记新关联，不要求为升级模板重建运行资料。
