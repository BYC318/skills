# 项目接入与复用

## 技能与项目的边界

本技能负责独立聊天的职责、持久消息、需求修订、恢复对账及源码交付协议。跨聊天协调者负责调度与集成，不接管已分配给其他执行者的源码；单 Agent 及模块执行任务内部主 Agent 可在自身范围实现和验证。共享任务仍唯一维护指定公共路径，调整已分配职责前先核对在途动作并完成交接。同仓库模块只按明确清单 `cherry-pick -x` 消费共享任务代码，跨仓库公共依赖按已核实的项目依赖机制交付，全部约定交付齐备后按 [分支基线与集成规则](code-delivery.md) 集中 rebase 到启动时当前分支的最新 HEAD，再快进回写。

项目配置负责以下事实：项目根及规则入口、真实源码仓库、各端角色、提交授权、任务资料位置、验收流程、构建和设备约束。项目的截图工具、设计服务、台账格式和验收册由项目自己的流程维护。本技能不复制它们，也不把某项目的截图数量推广到其他项目。

项目配置、长期目录、批次配置是三个不同层次：项目配置给出规则与路径；长期目录保存真实聊天及历史批次；批次配置冻结这一轮的参与者、授权、需求和实际工作区。模板中的示例角色与路径不代表任务已创建或操作已授权。共享任务为可选角色，按[职责与触发条件](../SKILL.md#共享任务的职责与触发条件)登记类型、权威来源、消费者及交付方式；不按平台组合预置实际任务。

多级协作按 [协调组与层级绑定](hierarchical-coordination.md) 为每组保留独立长期目录和批次；父子关系、消息映射及仓库集成归属由 Agent 核实，脚本不自动递归或转发。单层项目不要求补齐端内协调聊天，已有记录不重建。

## 配置定位与绑定

1. 从当前任务明确提供的配置、项目 AGENTS.md 的入口，或已核实的长期目录 `project_config` 定位配置。出现多份不一致配置时先核对本批快照与最新用户要求，不按技能附近文件猜选项目。
2. 使用 [项目协作配置模板](../assets/项目协作配置模板.md) 创建项目资料。项目根按配置声明解析，其他相对路径从项目根解析；技能内部链接始终从技能文件所在目录解析。解析后核实真实绝对路径、Git 根及逐级规则，不能把路径存在当成授权。
3. 新长期目录与新批次的 `project_config` 记录配置的实际绝对路径。分派前保存当批配置快照与 SHA256 到批次交付资料，通知各执行者该快照和实际规则入口。配置、权限或验收变化时评估在途动作与证据影响，保留旧快照，不默默替换已冻结依据。
4. `project_config` 是供 Agent 读取的可选元数据，脚本不解析其内容、校验哈希或执行里面的命令；实际授权、配置一致性和验收仍由任务核对。现有 schema 1、消息 envelope、动作身份及 CLI 均不改变。
5. 旧批次缺少此字段时，从原入口和可信记录核对并在接续说明中补记配置关联；继续用原 `--root` / `--registry`、逻辑 ID、消息 ID 和动作记录恢复。不得为补字段重建批次、改写不可变事件，或将已完成接入视作首次动作。

项目配置按真实源码位置登记与各源码仓库并列的 worktree 根，原仓库同父目录时共用一个根，否则按仓库分别登记；显式相对路径仍从配置声明的项目根换算，不默认指向协作目录下的 `worktree/`；目录布局和聊天/分支对应以[工作区目录规则](worktree-layout.md)为准。构建与证据目录仍由项目和机器约束决定，不能把源码工作区根当作统一产物目录。

## 分支与集成记录

实际启动时在 `batch.json.repositories` 填写 [启动快照](code-delivery.md#启动分支开发基线与-worktree)，项目配置仅维护规则，不固定活动分支。`integration.json.repositories` 引用同一仓库/目标/启动 SHA，并记录每次读取的目标 HEAD 与实际集成工作区，可安全复用原目标工作区或按需隔离；`rebases` 保存各次变基的意图、基点、输入/输出及 SHA 映射，`target_writebacks` 保存期望目标 HEAD、实际回写前后 SHA、状态和依据。目标继续正常推进时持续追加实际记录，不覆盖启动快照或旧交付。

批次 `integration_policy.method`、上述数组与目标分支元数据均由 Agent 维护；schema 1 和消息 CLI 不变，脚本不会自动创建 worktree、rebase、更新目标或核验 Git。旧批缺失信息时先从原授权、记录和真实 Git 查证并补入接续说明，不能把现在的分支冒充历史启动分支，也不因模板升级重做已完成动作。

## 验收接入

配置必须明确验收类型及其规则入口。UI 项目列出设计来源、参与平台、主题/方向等证据矩阵、采集与台账工具、通过条件和历史保存规则。非 UI 项目登记契约、测试、构建及所需产物；不要求安装 Figma 或双端技能。

执行者按项目流程生成证据，主任务核对来源及结果。需求变化使受影响证据失效，复验产生新轮次；依赖关闭、源码集成与最终验收始终分别记录。缺少必须的规则、工具或证据时保留阻塞/待验证；不能把恢复工具的 `RESOLVED` 当作验收通过。

## 在其他项目使用

可显式引用这份技能的实际绝对路径，或将整个 `codex-task-coordination/` 目录作为独立技能包安装到目标项目/用户技能目录。包内 `SKILL.md`、`agents/`、`references/`、`assets/`、`scripts/` 一起保留，其他项目无需原项目的相邻技能。采用一个明确的维护来源，避免同一项目存在多个同名入口；用户级安装应按目标环境和用户授权处理。

目标项目建立自己的配置，并在 AGENTS.md 写明：

> 仅在用户主动点名 `$codex-task-coordination`、明确要求使用该技能，或明确继续已启用该技能的协作任务时，读取本项目配置并按技能调度、通信、恢复与验收。普通开发不自动触发；本轮正常接续无需反复点名。任务资料和授权只使用本项目实际记录。

所有命令中的 `.agents/skills/codex-task-coordination/` 是项目安装方式示例。共享引用或用户级安装时，换成实际技能绝对路径；`--root` / `--registry` 始终指向调用项目自己的资料。不同项目不得共享一份运行目录。工具目前使用 Python 3 标准库和 POSIX 文件锁，面向 macOS/Linux 本机共享存储；跨机器通信和 Windows 运行未由本技能实现。

合成模块、共享能力和模拟 Git 仓库仅为回归夹具；运行协议按实体 ID、修订、角色和回执处理，不按业务名称分支。迁移时只携带技能包和未填写的模板，不复制原项目的任务目录、聊天 ID、消息、执行意图、源码授权或真实截图。
