# 复用与实现成本取舍

先寻找已有能力，再选择整体收益更高的实现。复用是减少重复和维护负担的手段；当改造、迁移、性能与回归验收的总成本明显高于新写时，可以选择新实现。保留项目既有风格，避免局部收益换来更大的耦合与验收成本。

## 快速参考

| 情况 | 先做什么 | 可接受结论 |
| --- | --- | --- |
| 新增能力 | 在相关范围内查项目、相邻模块、依赖和平台能力 | 直接复用或局部适配 |
| 复用需要改造 | 比较对旧调用方、依赖、性能和回归面的影响 | 有收益的改造，或职责明确的新实现 |
| 本地方案不足且外部能力可能有价值 | 聚焦查官方资料或维护来源 | 按需复用外部能力，不默认增加依赖 |

## 决策流程

1. 从当前需求、调用方、平台／版本和约束确定要交付的行为，再检查相关上下文；不要被已有半成品或某种设计模式预先限制方案。
2. 在与任务匹配的范围内检索项目、相邻模块、依赖、测试辅助代码和标准库／平台能力，确认公共入口与实际调用。简单任务做局部核对即可，不要求穷尽所有仓库或候选。
3. 比较直接复用、局部适配、改造现有实现和新写的总成本：实现工作量、迁移和兼容、旧调用方回归、验收、依赖与耦合、性能和资源、后续维护。已有稳定能力能低成本满足契约时优先复用；复用需要扭曲职责、扩大回归或付出明显更高成本时，允许新写。
4. 本地方案不足且外部能力可能带来实际收益，或关键 API／版本事实不确定时，再聚焦查询官方资料与维护来源。考虑新增依赖时，评估许可证、安全、维护状态、兼容性、体积、传递依赖和接入成本；不要为了走完流程给小函数做全网选型。
5. 选择后控制改动边界。保留既有风格和可复用的基础能力；新写不自动授权替换全部旧调用方或清理无关代码。公共改造覆盖受影响旧路径，新实现解释与既有能力的职责边界，避免长期维护无差别双轨。实质扩大架构、依赖或业务范围时按当前任务边界处理。

存在实质取舍时，用几句话说明选择；无需证明其他所有方案都不可行，也不强制每次输出表格或量化评分。说明只需覆盖与当前决策有关的内容：

- 已核对的候选和关键限制；
- 选择复用、改造或新写的整体收益，以及维护和验收成本；
- 实际改动范围与必要验证；尚未确认的性能收益保持未验证。

复用时只说明复用目标和必要适配，不制造长报告。

## 网络不可用

完成必要的本地核对；实际需要外部查询但不可用时，说明“外部候选／资料未验证”，不得伪称已检索。契约明确且现有证据足以支持低风险方案时继续；只有未确认事实会影响安全、正确性或实质取舍时才询问，不为例行选型阻塞开发。

## 例子

需求：增加跨平台重试工具，已有一半实现。

先定义取消、退避、错误分类和线程边界，检查现有重试器。能通过小适配满足时复用；若适配要重构大量旧调用方且扩大验收面，而本次只需一个职责清楚的小实现，可保留既有调度基础并新写局部策略。按取消、次数和退避验证实际行为，不顺手迁移其他模块。

对于两个看起来相似、但业务语义和变化方向不同的小函数，可以暂时保留清晰的独立实现；出现真实共同需求后再抽取，避免以复杂参数和隐式耦合换取表面去重。

## 常见借口与纠偏

| 借口 | 纠偏 |
| --- | --- |
| “赶时间，先写。” | 先做有范围的本地检索。 |
| “只有几行。” | 做局部核对；不跳过已有能力，也不把小改动升级为通用框架。 |
| “已经写一半。” | 按后续总成本选择，半成品不是继续投入的充分理由。 |
| “开源库更可靠。” | 先比较依赖总成本与最小本地实现。 |
| “已经有了就必须复用。” | 比较改造、耦合和回归验收成本，代价更高时允许新写。 |

## 红旗

- 未写契约就创建通用抽象。
- 未查已安装依赖或平台能力就新增依赖。
- 以“成熟”“常用”替代许可证、安全和兼容性评估。
- 网络不可用却声称外部候选已验证。
- 为少几行代码制造难懂抽象，或为局部性能微调扩大改动与验收面。
- 明知复用改造总成本更高仍强制复用，或借新写之名无边界重构旧模块。
