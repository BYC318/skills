# 复用优先

## 快速参考

| 情况 | 先做什么 | 可接受结论 |
| --- | --- | --- |
| 新增通用能力 | 查项目、相邻模块、依赖和平台能力 | 复用或最小适配 |
| 本地候选不足 | 查官方资料和成熟 GitHub 开源库 | 引入经评估的依赖 |
| 仍不合适 | 限定最小边界后自写 | 小而可验证的实现 |

## 决策流程

1. 先说明要交付的契约、调用方、平台/版本、性能与安全边界；不要先从代码或半成品推导需求。
2. 检索当前项目、相邻模块、本地 Package、测试辅助代码、已安装依赖与标准库/官方平台能力。检查公共入口和依赖，而非因半成品写到一半就补完重复抽象。
3. 判断能否直接复用，或以不破坏边界的最小适配满足契约。
4. 确有缺口时，再检索官方来源及成熟 GitHub 开源库；逐项评估许可证、安全、维护活跃度、平台兼容性、体积与传递依赖、接入和长期维护成本。
5. 在复用、适配、引入依赖与自写之间选择。外部库不是默认答案；领域适配、简单胶水、供应商/安全隔离，或极小且清晰的逻辑可以自写。

仅在现有能力与合适外部方案都无法满足时，才编写非平凡新实现。自写前先输出简短决策记录：

- 检索范围与关键词；
- 找到的本地、官方和开源候选；
- 每个候选的具体拒绝理由；
- 最小自写边界与验证方式。

复用时只说明复用目标和必要适配，不制造长报告。

## 网络不可用

完成本地检索，并明确“外部候选未验证”；不得伪称已搜索官方或 GitHub。若契约明确且风险低，可做最小本地实现；否则请求用户决定是否等待外部评估或接受实现风险。

## 例子

需求：增加跨平台重试工具，已有一半实现。

先定义取消、退避、错误分类和线程边界；检索 `retry`、`backoff`、现有网络层与依赖。若项目已有可取消重试器，只补一个领域适配；若它缺少必要契约且官方/开源候选引入成本过高，记录缺口后只实现无状态重试核心，并用取消、次数和退避测试验证。半成品本身不是采用理由。

## 常见借口与纠偏

| 借口 | 纠偏 |
| --- | --- |
| “赶时间，先写。” | 先做有范围的本地检索。 |
| “只有几行。” | 核对公共入口；小代码也会制造第二套能力。 |
| “已经写一半。” | 检查是否重复；可删弃半成品。 |
| “开源库更可靠。” | 先比较依赖总成本与最小本地实现。 |

## 红旗

- 未写契约就创建通用抽象。
- 未查已安装依赖或平台能力就新增依赖。
- 以“成熟”“常用”替代许可证、安全和兼容性评估。
- 网络不可用却声称外部候选已验证。
- 因时间压力、半成品或小需求跳过检索与决策记录。
